# 0003: Tax

- **Status:** Accepted (2026-10-13). T1–T4 and T9–T10 were decided in conversation;
  T5–T8 were proposed and not objected to.
- **Scope:** built-in, rate-table tax for carts (and, later, orders). External tax
  engines (Avalara, Stripe Tax, US ZIP-level rates) are spores behind a port that comes
  later; this note only makes sure the types fit it.
- **Related:** 0002 (closed aggregates, extensions link by ID; tax engines are named as
  spore material).

## Decisions

| | Decision |
| --- | --- |
| T1 | Whether prices include tax is set **per market** (`prices_include_tax`) |
| T2 | A cart has a **country**, which must belong to its market; it picks the rates |
| T3 | Product-specific rates come from **tax classes owned by `hypha-tax`**, linked to products by ID |
| T4 | Built-in rate tables now; a `TaxProvider` port later, so request/result types are shaped for it |
| T5 | Rates are `TaxRate` in parts per million, not `BasisPoints` |
| T6 | Tax is computed **per line**, rounded half away from zero, then summed |
| T7 | A country with no tax region is charged no tax |
| T8 | Inclusive prices stay as entered in every country of the market; tax is extracted at the destination rate |
| T9 | `create_cart` takes only a country and resolves the market from it (like Shopify); the cart stores both |
| T10 | No backfill: the `country` column is added `NOT NULL`, existing carts are dropped (no real data yet) |

## 1. What others do

**Shopify**
- A product's tax treatment comes from its taxonomy `category`, which is stored on the
  product, not the variant. Shopify Tax uses it to pick rates.
- Merchants override rates per country through **collections**, not through a named
  tax class.
- `ProductVariant.taxable` is the only tax field left on the variant; `taxCode` is
  deprecated.
- Tax display (inclusive or not) is set per market.

**Medusa v2**
- A tax module owns `TaxRegion` (country, optional province), `TaxRate` (`is_default`,
  `is_combinable`) and `TaxRateRule` (`reference`, `reference_id`, matching `product`,
  `product_type` or `shipping_option`).
- The product module has no tax fields.
- A fixed precedence picks one rate: product rule, then type rule, then the region's
  default, with a province beating its country.
- `is_tax_inclusive` lives on a price preference (per region or currency).
- Cart and order lines store snapshot tax lines (`rate`, `code`, `provider_id`,
  `tax_rate_id`).

**What we take from them**
- Keep tax off the product aggregate (both do, except Shopify's category).
- Keep inclusiveness off the product and on the market.
- Use explicit precedence and snapshot tax lines.

**What we don't take**
- **Medusa's per-product rules don't scale** to large catalogs: one rule row per product,
  per rate, per country.
- **A class is one level of indirection:** a product is assigned to a class once, and each
  country prices the class. That fits EU VAT, where each member state maps the same
  categories (books, food, …) to its own reduced rates.
- **Hypha has no product types or manual collections**, so there's nothing else to hang
  rules on yet.

## 2. Model (`hypha-tax`, a leaf crate depending only on core)

**`TaxRate` (in `hypha-core::money`)**
- Parts per million, from 0 to 1,000,000 (0% to 100%). Some US rates have three
  decimals, such as 8.875% (`88_750`), and `BasisPoints` can't represent them (T5).
- `tax_on_net` and `tax_in_gross` use `i128` intermediates and round half away from zero,
  like `Money::adjust`. An invalid rate is `MoneyError::InvalidTaxRate`.

**`TaxClass` aggregate (`txc_…`)**
- Fields: `name` only. Classes are referenced by ID; a unique handle can come later if
  admins or agents need one.
- Assignments are a link `product → class` in the tax crate's own table (product level,
  like Shopify's category).
- A product without a class is "standard".
- A tax-exempt product is simply a product in a class rated 0%, so no `taxable` column
  is needed on variants.

**`TaxRegion` aggregate (`txreg_…`)**
- Fields:
  - `country`, a unique key: one region per country
  - `default_rate: TaxRate`
  - `class_rates: Vec<(TaxClassId, TaxRate)>`, each class at most once
- The region owns its class rates, the same way a product owns its variants.
- Reserved for later: an optional subdivision (US states, CA provinces) and Medusa-style
  `is_combinable`. That territory mostly belongs to external engines, so neither is
  built now.

**Ports (`repo.rs`)**
- `TaxClassRepo`: get, insert, a batched
  `classes_for(&[ProductId]) -> HashMap<ProductId, TaxClassId>`, and a batched
  `assign(&[ProductId], Option<TaxClassId>)`. The assignment is a link row, not an
  aggregate, the same as catalog membership. (No update yet: nothing renames a class.)
- `TaxRegionRepo`: get, get_by_country, insert/update.

**Resolution (pure)**
- Signature: `tax_line(ctx: &TaxContext, line: &TaxableLine) -> Result<Option<TaxLine>, MoneyError>`.
  The context (region, `prices_include_tax`, product classes) is plain data loaded in
  batches, like `PricingContext`.
- Precedence:
  1. The product's class rate in the destination country
  2. Otherwise, the country's default rate
  3. Otherwise, no region for the country, so no tax (T7)
- A class rated in some countries and not others falls back to the default in the
  others.

**Request and result shapes for the later port (T4)**
- `TaxableLine`: `{ product, amount: Money }`. An engine will want more (variant,
  quantity, address); fields get added when the port exists.
- `TaxLine`: `{ rate: TaxRate, class: Option<TaxClassId>, amount: Money, source: TaxSource }`
- `TaxSource` is an enum with a single `RateTable { region }` variant today. A spore
  would add its provider ID, and `data` later.

## 3. Arithmetic (T6, T8)

Let `r` be the rate in parts per million and `p` the line total (unit price × quantity):

- **Exclusive:** `tax = round(p × r / 1_000_000)`, and the line costs `p + tax`.
- **Inclusive:** `tax = round(p × r / (1_000_000 + r))`, and the line costs `p`. The net
  amount is `p − tax`.

Both are computed with `i128` and rounded half away from zero, once per line. The cart
total is the sum of the rounded line amounts, so the lines always add up to the total.

T8 means a €10.00 inclusive price costs €10.00 in Croatia (25%) and in Germany (19%);
the merchant's margin varies, not the shelf price. Shopify's "dynamic tax-inclusive
pricing" (re-pricing per country from a home rate) is out of scope. It ignores
overrides and fixed prices anyway.

## 4. Changes to existing crates

**`hypha-markets`: `Market` gains `prices_include_tax: bool` (T1)**
- `create_market` takes it (`false` if omitted over HTTP); `set_prices_include_tax`
  changes it (`PATCH /markets/{id}`).
- `MarketRepo` gains `get_by_country`.
- Migration: `ALTER TABLE markets ADD COLUMN prices_include_tax boolean NOT NULL DEFAULT false`.

**`hypha-cart`: `Cart` gains `country: CountryCode` (T2, T9, T10)**
- `create_cart` takes only the country and finds its market with
  `MarketRepo::get_by_country`; no market covering it fails with `no_market_for_country`.
- The migration deletes existing carts and adds a `NOT NULL` column (no real data yet).
- A cart keeps its market and country even if the market later drops the country.
  Re-resolving the market is future work.

**`hypha-cart` → `hypha-tax`**
- This is a new edge, from a composing domain to a leaf, which the layering table
  allows.
- `CartPorts` gains `TaxClasses` and `TaxRegions`, and `price_cart` takes a `TaxContext`.
  Loading it adds two queries per cart (8 in total): the region by country, and the
  classes of the cart's products.
- `LineStatus::Priced` gains `tax: Option<TaxLine>`. `PricedCart` becomes:
  - `subtotal`: the sum of the line amounts as entered
  - `tax_total`
  - `total`: `subtotal + tax_total` when prices exclude tax, otherwise `subtotal`
  - `taxes_included`
- Carts compute tax on read and store nothing. Orders will snapshot `TaxLine`s.

**`hypha-core`**
- `TaxRate`, plus `TaxClassId` (`txc`) and `TaxRegionId` (`txreg`).
- Scopes `taxes:read` and `taxes:write`.

**`hypha-store-postgres`**
- Tables `tax_classes`, `product_tax_classes` (product ID as the primary key, with no
  foreign key into products, per 0002), `tax_regions` and `tax_region_class_rates`.
- Repo contract scenarios come first, in `hypha_testkit::contract`.

**`hypha-host-axum`**
- `routes/taxes.rs`:
  - `POST /tax-classes`
  - `PUT /tax-assignments` (`{products, tax_class}`, `null` to unassign)
  - `POST /tax-regions`, `GET` and `PATCH /tax-regions/{id}`
  - `PUT` and `DELETE /tax-regions/{id}/class-rates/{class_id}`
- `POST /carts` takes `country`. Cart responses gain the tax fields.
- e2e steps for each new route.

**Error codes (new)**
- `invalid_tax_rate`
- `tax_class_not_found`
- `tax_region_not_found`
- `tax_region_exists` (the country is taken)
- `class_rate_not_found`
- `duplicate_class_rate` (stored data only). *Removed:* only `TaxRegion::restore` can
  hit it, so it became `hypha_tax::RestoreError` (review D4) and never reaches the API.
- `no_market_for_country`

## 5. Build order

Each step is its own commit and passes the four checks in CLAUDE.md, so a step that
changes a domain type also updates the adapter and host code that use it.

1. `feat(core)`: `TaxRate`, the IDs and the scopes.
2. `feat(tax)`: the crate, its testkit repos and contract.
3. `feat(markets)`: `prices_include_tax` and `get_by_country`, with migration 4 and the
   host's market routes.
4. `feat(store-postgres)`: tax tables (migration 5) and repos.
5. `feat(cart)`: `country` on carts and tax in pricing, with migration 6, `CartPorts`
   implementations and the cart routes.
6. `feat(host-axum)`: tax routes, error mapping, e2e.

## 6. Later

- **Shipping tax** comes with shipping, which doesn't exist yet. `TaxableLine` will gain
  a kind (`Item` or `Shipping`) then.
- **Customer exemptions** (B2B reverse charge, exempt organisations). Customers arrived
  (0005) without them: deferred again, with customer groups. Shopify checks them before
  overrides.
