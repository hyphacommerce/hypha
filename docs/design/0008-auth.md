# 0008: Staff auth, roles and API keys

- **Status:** Accepted and built (2026-10-14, branch `feat/auth`). Danilo settled the
  open questions in conversation: server-side sessions, not JWTs (A3);
  authenticator-app 2FA built in from the start (A5); write scopes imply read (A7);
  email goes through a port (A10). Everything else is as recommended. Changes made
  while building are marked in place.
- **Scope:** who is calling and what they may do. That covers staff users, roles, invites,
  password login, sessions, 2FA (TOTP and recovery codes), password reset, and secret
  and publishable API keys. Also the `Caller` extractor that turns a request into a
  `Ctx`.
- **Not in scope:** customer accounts, OAuth apps (third parties installing into a
  store), SSO/OIDC, passkeys, login rate limiting, an admin panel, and the storefront and
  admin API split. The model leaves room for each (section 9).
- **Related:** 0002 (external apps and API keys), 0006 T4 (staff and keys live in the
  store's database), 0007 (batches, idempotency).

## Decisions

| | Decision |
| --- | --- |
| A1 | **Three kinds of caller:** staff users (sessions), API keys (scripts, integrations, storefronts) and, later, customers. Each becomes a `Ctx` in one place, `Caller` |
| A2 | **An identity has many credentials** (password, TOTP, recovery codes; later OIDC and passkeys). A new login method is a new credential kind, with no new table. The identity belongs to a typed principal (`Staff(UserId)`, later `Customer(CustomerId)`), not to stringly JSON as in Medusa |
| A3 | **Server-side sessions, not JWTs.** A session token is random and opaque, and only its SHA-256 is stored. Every request looks the session up, so logout, a disabled user or a changed role take effect on the next request |
| A4 | **Login is first factor → challenge → session.** If the identity has a second factor, a correct password opens a *pending* session: short-lived (5 min), at most 5 attempts, usable only to finish the login. The second factor activates it under a new token |
| A5 | **TOTP and recovery codes from day one**, with the TOTP secret encrypted at rest. Passkeys and security keys are later credential kinds behind the same challenge |
| A6 | **Roles are named sets of scopes, in the open core.** A user has one role. The built-in `Owner` role has every scope, including scopes added in later versions. Nobody can grant a scope they don't hold |
| A7 | **A write scope implies its read scope** (`products:write` grants `products:read`), as in Shopify. `Ctx` applies it, so roles and keys list less |
| A8 | **Secret and publishable API keys.** Secret keys carry chosen scopes and are for servers. Publishable keys carry the fixed storefront scopes and may sit in a browser. Both are shown once, stored hashed, displayed redacted and revocable |
| A9 | **Prefixed tokens:** `hypha_sk_`, `hypha_pk_`, `hypha_sess_`, `hypha_inv_`, `hypha_rst_`, followed by 32 random bytes as hex. The prefix tells the host which lookup to run and lets secret scanners spot leaks |
| A10 | **Email through a port.** Domain crates hand typed messages (`Invite`, `PasswordReset`) to a `Notifier`; hosts render and deliver them. Locally, the host logs them |
| A11 | **Bootstrap from the environment:** with no staff user yet, `HYPHA_OWNER_EMAIL` and `HYPHA_OWNER_PASSWORD` create the owner at startup |
| A12 | **Two crates:** `hypha-auth` (leaf: identities, credentials, sessions, API keys, password resets) and `hypha-users` (composing over auth: users, roles, invites and the staff login flows) |

## 1. What others do

Researched 2026-10-14.

**Shopify**
- **Apps:** OAuth authorization code, with tokens bound to one shop. Since Dec 2025 offline
  tokens can expire after 1 h, with a refresh token (90 days) that rotates on each use.
  New public apps must use them from April 2026, all public apps from 2027. Scopes are
  `read_x` / `write_x`, and write implies read. Each installation stores the scopes it
  was granted. An app acting for a staff member (an "online" token) gets only the
  scopes both have.
- **Staff:** granular permissions grouped into roles. 2FA by authenticator app,
  security key or passkey, plus recovery codes. SMS can't be newly added any more. SAML
  SSO on Plus.
- **Customers:** password accounts were deprecated in Feb 2026. New accounts sign in
  with a 6-digit email code, Google or passkeys, through an OAuth/OIDC API with PKCE.
- **Storefront:** a public token for browsers, a private token for servers.

**Medusa v2** (v2.21)
- `auth_identity` has many provider identities (email and password, Google, …). A provider
  implements `authenticate` / `register` / `validateCallback`. The identity links to
  its user or customer through `app_metadata.user_id` (untyped JSON).
- Login issues a JWT (default 1 day) carrying the actor. Nothing revokes it.
- MFA since v2.15.5 (June 2026): TOTP and recovery codes, applied after any first
  factor. The first step returns a token that can only finish the login. Routes can
  demand a recent MFA check. TOTP secrets are encrypted.
- API keys: publishable (sent in a header, scoped to sales channels) and secret
  (salted hash, redacted, revocable).
- Admin invites. No permissions in the MIT core: roles (RBAC) are in the paid
  Enterprise edition.

**What we take:** identity, credential and actor kept separate; MFA as a layer after
any first factor; pending login tokens; publishable and secret keys (Medusa). Roles as
sets of scopes, write-implies-read, the scope intersection for agents and apps, and
expiring and rotating tokens for apps later (Shopify).

**What we don't take:**
- Medusa's JWTs, since a removed permission keeps working until the token expires.
- Medusa's untyped identity links.
- Medusa's two-step registration that can leave orphan identities. Our invite
  acceptance is one batch.
- Shopify's legacy static tokens and SMS codes.

## 2. Model

### `hypha-auth` (leaf)

**`Identity` (`idn_…`)**
- `principal: Principal`: `Staff(UserId)` for now. A `Customer(CustomerId)` arm comes with
  customer accounts.
- `credentials: Vec<Credential>`, owned like a product owns its variants:
  - `Password { email, hash }`. `email` is the login name, lowercased; `hash` is a PHC
    string (Argon2id).
  - `Totp { secret: Sealed, confirmed: bool, last_step: Option<u64> }`. Unconfirmed
    while being set up. `last_step` rejects a code that was already used.
  - `RecoveryCodes { hashes: Vec<TokenHash> }` (SHA-256), each single use.
- Unique key `identity_login`: a principal kind (staff or customer) plus a credential's
  lookup (for a password, the email). So a staff member and a customer may share an
  email, but two staff members may not.
- In Postgres, one row per credential: `kind`, a nullable `lookup` with the unique index,
  and `data jsonb`. A new credential kind (OIDC with issuer and subject as its lookup,
  a passkey with its credential ID) needs no migration.

**`Session` (`sess_…`)**
- `identity`, `principal`, `token_hash` (unique), `created_at`, `expires_at`,
  `revoked_at`.
- `state`:
  - `Pending { attempts }`: first factor done; only `finish_login` accepts it.
  - `Active { mfa_at: Option<Timestamp> }`: when the second factor was last proven, for
    step-up later.
- Lifetimes: 5 minutes pending, 7 days active. Activation issues a new token, so the
  pending token can't be replayed and a token issued before login can't be "fixated".

**`ApiKey` (`key_…`)**
- `kind`: `Secret` or `Publishable`.
- `name`, `token_hash` (unique), `last_four`.
- `scopes`: chosen for a secret key; `Scope::STOREFRONT` for a publishable one.
- `created_by: Actor`, `created_at`, `revoked_at`.
- A key belongs to the store, not to the user who made it, so disabling that user
  doesn't break the integration.

**`PasswordReset` (`pwr_…`)**
- `identity`, `token_hash` (unique), `expires_at` (1 hour), `used_at`.

**Ports**
- `Random` (core): fills a byte buffer. Hosts use the OS generator; tests use a
  deterministic one. Every token, salt, nonce and recovery code comes from here.
- `PasswordHasher`: `async fn hash` and `async fn verify`. The default is Argon2id with
  OWASP's parameters (19 MiB, 2 passes, 1 lane). The axum host runs it on a blocking
  thread so a login doesn't stall other requests. It's async so a Workers host can
  offload it later.
- `SecretBox`: `seal` and `open`. XChaCha20-Poly1305 under a 32-byte key the host reads
  from `HYPHA_SECRET_KEY`. A sealed value starts with a version byte, so the key can
  rotate later. The identity's ID is bound in as associated data, so a sealed secret
  copied onto another identity doesn't open. With Postgres the host refuses to start
  without the key; in memory it makes a throwaway one.

### `hypha-users` (composing, depends on `hypha-auth`)

**`Role` (`role_…`)**
- `name` (unique).
- `scopes: RoleScopes`, either `All` (the built-in owner) or `Only(Vec<Scope>)`.
- The owner role can't be edited.

**`User` (`user_…`)**
- `email` (unique), `name`, `role: RoleId`, `status: Active | Disabled`.
- The user is the person; how they log in lives in their identity.

**`Invite` (`inv_…`)**
- `email` (unique), `role`, `token_hash` (unique), `expires_at` (7 days),
  `invited_by: UserId`, `accepted_at`.
- Inviting the same email again replaces the pending invite: new token, new expiry,
  possibly a new role. That's how an admin resends one, or retries after the email
  failed.

## 3. Login (A4)

```text
POST /auth/login {email, password}
  ├─ wrong email or password ─→ 401 invalid_credentials (same answer and roughly the
  │                              same time for an unknown email: a dummy hash is checked)
  ├─ user disabled ───────────→ 401 invalid_credentials
  ├─ no second factor ────────→ 200 {"status": "authenticated", "session": {token, expires_at}}
  └─ TOTP confirmed ──────────→ 200 {"status": "mfa_required",
                                     "challenge": {token, methods: ["totp", "recovery_code"], expires_at}}

POST /auth/login/mfa {challenge, code}
  ├─ wrong code ─→ 401 invalid_mfa_code (the 5th wrong code revokes the challenge)
  └─ right code ─→ 200 {"status": "authenticated", "session": {…}}, under a new token
```

*Changed while building:* no `method` field. A TOTP code is 6 digits and a recovery code
16 base32 characters, so the code says which it is.

- **TOTP** follows RFC 6238: HMAC-SHA1, 6 digits, 30-second steps. One step of drift is
  accepted either way, and a step at or before `last_step` is refused.
- **Recovery codes:** 10 codes of 16 base32 characters (80 bits), stored as SHA-256. A
  slow hash isn't needed at 80 bits, the same reasoning as for tokens. Each code works
  once.
- **Requests:** a session or API key goes in `Authorization: Bearer <token>`. A
  publishable key may also go in `X-Publishable-Key`, so a storefront can later send a
  customer session beside it.
- **Errors:**
  - No credentials is `401 unauthenticated`.
  - An unknown, expired, revoked or pending token is `401 invalid_token`, and so is a
    disabled user.
  - A valid caller without the scope stays `403 missing_scope`.
  - 401 responses carry `WWW-Authenticate: Bearer`.

## 4. Roles, scopes and escalation (A6, A7)

- **Per request:** the session's user, then the user's role, then the scopes, so `Ctx`
  is fresh.
- **`Ctx::has_scope(read)`** is true if the caller holds the read scope or its write
  twin. `Scope::implied_by` holds the pairs, and `checkout` implies nothing.
- **New scopes:**
  - `users:read`, `users:write`: users, roles and invites.
  - `api_keys:read`, `api_keys:write`.
- **No escalation:** creating or editing a role, inviting with a role, changing a user's
  role, and creating a secret key all require the caller to hold every scope given away
  (`not_allowed_to_grant`, 403). An owner can grant anything.
- **Lockout guard:** the last active owner can't be disabled or moved to another role
  (`last_owner`, 409).
- **Storefront scopes (`Scope::STOREFRONT`):** `products:read`, `markets:read`,
  `carts:write` (and through it `carts:read`), `checkout` and `stores:read`. Until the
  storefront and admin API split, a publishable key reads what those scopes read on the
  current routes. It can't create customers, mark orders paid or see orders.

## 5. Invites and password reset

- `POST /invites {email, role}` stages the invite, commits, then sends the email. If
  sending fails, the invite exists and the error says so (`email_failed`, 502). Inviting
  again replaces the token.
- `POST /invites/accept {token, name, password}` makes the user, the identity with its
  password, the accepted invite and an active session in one batch. The response is the
  session, so accepting logs you in.
- `POST /auth/password-reset {email}` always answers 202, so it doesn't reveal which
  emails exist. A send failure is logged.
- `POST /auth/password-reset/confirm {token, password}` sets the password, uses up the
  token and revokes every session of the identity, all in one batch.
- **Passwords:** 8 to 128 characters. A reset or change doesn't touch 2FA.

## 6. "Me" routes

The caller must be a staff session; an API key gets `401 session_required`.

- `GET /me`: the user, the role, the effective scopes, and whether 2FA is on.
- `PUT /me/password {current_password, new_password}`: revokes every other session.
- `POST /me/mfa/totp`: starts setup and returns `{secret, uri}` (`otpauth://…`) for the
  authenticator app. Starting again replaces an unconfirmed setup. `409 mfa_enabled` if
  2FA is already on.
- `POST /me/mfa/totp/confirm {code}`: turns 2FA on and returns 10 recovery codes, shown
  only this once.
- A wrong code on these routes is `422 invalid_mfa_code`, not the 401 a login gets: the
  caller is logged in, and a 401 would tell clients their session died. A wrong
  current password is `422 wrong_password` for the same reason.
- `POST /me/mfa/totp/disable {code}`: takes a TOTP or recovery code and removes both
  factors.
- `POST /me/mfa/recovery-codes {code}`: replaces the recovery codes.

Step-up is reserved but not built: `Session::mfa_at` records when 2FA was last proven,
and a later command can require it to be recent. Until then the disable and regenerate
routes ask for a current code instead.

## 7. Email (A10)

```rust
// hypha-core
pub trait Notifier<M> {
    async fn notify(&self, message: M) -> Result<(), NotifyError>;
}

// hypha-users
pub enum StaffEmail {
    Invite { to: Email, token: String, expires_at: Timestamp },
    PasswordReset { to: Email, token: String, expires_at: Timestamp },
}
```

- **The host renders the message.** It knows the admin panel's URL (`HYPHA_ADMIN_URL`)
  and turns the token into a link. Domain crates never see URLs or templates.
- **Delivery:** the axum host logs the rendered email, tokens included, and warns at
  startup that this is for development only. An SMTP or Resend sender is one more
  `Notifier` impl, and the first thing a real deployment needs.
- **Timing:** commands send after the commit. When the outbox exists (0002), the
  message will be staged in the same batch and sent by a worker, so a crash between
  the commit and the send no longer loses it.

## 8. Commands and environment

Auth commands need more non-storage ports than any command so far (IDs, clock, random,
hasher, secret box, notifier), so they take one `env: &E` bounded on a bundle trait
instead of six parameters:

```rust
pub trait AuthEnv: IdGenerator + Clock + Random + PasswordHasher + SecretBox {}
impl<T: IdGenerator + Clock + Random + PasswordHasher + SecretBox> AuthEnv for T {}
```

This is the same blanket-impl trick as `CartPorts`. The host implements each trait once
on its environment type; `hypha-testkit` has a deterministic one.

Storage follows 0001 and 0007:
- Repos: `IdentityRepo`, `SessionRepo`, `ApiKeyRepo`, `PasswordResetRepo`, `UserRepo`,
  `RoleRepo`, `InviteRepo`.
- `Stage*` traits for the batched flows: accept invite, reset password, finish login.
- One contract scenario per repo.

**Resolving a caller** (host, `Caller`), by token prefix:
- `hypha_sess_`: `hypha_users::authenticate_staff` gives `Ctx(Actor::User, role scopes)`.
- `hypha_sk_` or `hypha_pk_`: `hypha_auth::authenticate_api_key` gives
  `Ctx(Actor::ApiKey, key scopes)`.

`Actor` gains `ApiKey(ApiKeyId)`. `Agent` stays for admin assistants. `Caller` is
implemented once per concrete storage (like `router!`), because axum must prove the
extractor's future is `Send`.

**Writes on read:** none. Recording when a key or session was last used would cost a
write on every request. It's a follow-up (section 9), throttled to once an hour.

## 9. Later, and how it fits

- **Login rate limiting:** a host layer (per IP and per email), next after this note.
  Until then, rely on Argon2's cost and the challenge's attempt limit.
- **Passkeys and security keys** (`webauthn-rs`): a credential kind, both as a second
  factor and as a passwordless first factor.
- **SSO/OIDC** (`openidconnect`): a credential kind with `(issuer, subject)` as its
  lookup, plus a redirect step (Medusa's `location`).
- **Customer accounts:** `Principal::Customer`. Email codes first (Shopify's new
  accounts) through the same identity, challenge and session pieces.
- **OAuth apps:** authorization code with PKCE, 1 h access tokens and rotating refresh
  tokens. Each installation stores its granted scopes. An app or agent acting for a
  user gets the intersection of the two scope sets.
- **Step-up** on `Session::mfa_at`, a store setting that requires 2FA for all staff,
  session listing and revoke-all, `last_used_at` on keys and sessions, and cookie
  sessions with CSRF protection for an admin panel on another origin.
- **Listing** users, roles, invites and keys, with the admin API work.

## 10. Hard to reverse

- **Token formats** (A9): clients and secret scanners match on them.
- **Sessions over JWTs** (A3): stateless hosts would need a different design.
- **Scope names and write-implies-read** (A7): once roles exist in a database, a scope
  can't be renamed without a data migration. Making read separate again would silently
  take access away.
- **Credential rows with JSON data** (A2): the extensibility relies on it.
- **Staff and keys in the store's database** (0006 T4): one login across stores would
  need a control plane.
