# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Hypha (working name): open-source, modular e-commerce API in Rust (edition 2024, Cargo workspace, `crates/*` and `spores/*`).
- **Modular**: one crate per domain; behavior is extended through plugins ("spores") via traits and events, not by editing core.
- **Agent-friendly, in two specific ways** (shopping agents are *not* the target of the core API):
  1. **Building Hypha**: the codebase is meant to be easy for coding agents to extend: core, domain crates and plugins ("spores"). Favor explicit types, small crates with clear ports, exact errors and fast deterministic tests over cleverness.
  2. **Admin assistance**: agents will help merchants operate the system from the admin panel. Every operation is a command with typed input, required scopes and typed errors, so the same surface can be exposed over HTTP, MCP and CLI; such agents act as `Actor::Agent` with their own scopes.
  - Agentic *shopping* goes through a separate adapter for the Universal Commerce Protocol (UCP, ucp.dev; planned via ucphub.ai), not through the core commands directly. Design storefront-facing read models (e.g. priced carts) so they map cleanly onto UCP, e.g. per-line problems → UCP `messages` with a `path` to the line.
- **Large catalogs**: sparse explicit variants (never generate the Cartesian product of options); Shopify-style markets / catalogs / price lists.
- **Multi-host**: the same core runs on Cloudflare Workers (WASM), AWS Lambda, Vercel and a plain VPS (axum).
- It's also a Rust learning project for the maintainer (Danilo, TypeScript background). See "Working with Danilo".

## Commands

Run all five before considering work done (and, for TypeScript changes, `pnpm fmt`, `pnpm lint`, `pnpm lint:react` and `pnpm typecheck`); CI (`.github/workflows/ci.yml`) runs them too, plus e2e and the TypeScript checks, with clippy warnings as errors (the tests need the compose services: `docker compose up -d`; they run on `postgres-test`, a throwaway in-memory Postgres at `HYPHA_TEST_DATABASE_URL`, each test on its own copy of a migrated template (`hypha_store_postgres::testing::TestDatabase`), while `DATABASE_URL` is the dev database the host uses; `.cargo/config.toml` sets both, and exported values win). Tests run with cargo-nextest (`cargo install cargo-nextest --locked`; `.config/nextest.toml` caps the Postgres and S3 tests' concurrency):

Extend the wasm build list when a domain crate or storage adapter is added. `hypha-http` is on it: anything a runtime provides goes through `host.rs`, never a Tokio or OS call (design note 0026).

- Dependencies and API compatibility (beside `ci.yml`): `deny.yml` runs `cargo deny check` (`deny.toml`: RustSec advisories, permissive licenses only, crates.io only; on Cargo changes, pushes to main and weekly) and `api-compat.yml` runs `oasdiff breaking` on each `openapi/*.json` against the pull request's base (`.oasdiff.yaml`; a new response enum value is only reported; label the PR `breaking-api` to ship a break on purpose). Run `cargo deny check` after adding a crate. Dependabot (`.github/dependabot.yml`) proposes weekly grouped updates, a week after release. Actions are pinned to commit SHAs with the version in a comment, and workflows read with `permissions: contents: read`.
- Single crate's tests: `cargo nextest run -p hypha-products` (`cargo test -p …` works too)
- Single test by name: `cargo nextest run -p hypha-products rejects_same_handle_products`
- Only an integration test file: `cargo nextest run -p hypha-products --test commands`
- Run the HTTP host (binds `server.bind`, `127.0.0.1:3000` by default; `RUST_LOG` respected; Ctrl+C or SIGTERM drains in-flight requests; `GET /health` for probes; `-- setup` does a start's preparation (migrations, store, owner, location, search index) and exits without serving): `HYPHA_SECRET_KEY=… cargo run -p hypha-host-axum`, on Postgres only (`DATABASE_URL`, the compose database by default under cargo; migrations run on startup). `HYPHA_SECRET_KEY` is 64 hex characters from `openssl rand -hex 32`, kept across restarts since it seals 2FA secrets. Every route but `/health` and the login ones needs credentials (design note 0008): on first start, `HYPHA_OWNER_EMAIL` and `HYPHA_OWNER_PASSWORD` create the owner, who logs in with `POST /auth/login`. Emails (invites, resets) are logged, not sent; `server.admin_url` turns their tokens into links. `server.public_url` (`HYPHA_PUBLIC_URL`, set by `hypha deploy`) is the API's public base URL for apps (the OAuth issuer, token answers, session tokens' `iss`); unset, it's derived per request, believing `X-Forwarded-Host`/`-Proto` only from `server.trusted_proxies`. The public routes are rate limited per client address (design note 0009): behind a proxy or load balancer, set `server.trusted_proxies` (CIDR ranges) so `X-Forwarded-For` is believed from those peers, or every client shares one limit (a server-rendered storefront is such a proxy: it passes shoppers' addresses). Calls to merchant-configured URLs (rate apps, webhooks) reach only public addresses and are signed with the app's secret (`outbound.rs`); `outbound.allow_private` (`HYPHA_ALLOW_PRIVATE_CALLBACKS=true`) allows localhost apps in development. Postgres uses TLS when the URL's `sslmode` asks for it (`prefer` by default, `require` for managed databases), verified against the OS trust store.
- Configuration (design note 0017): operator settings (bind address, proxies, body limit, pool, media, auth lifetimes, job switches and timers, the dispatcher's batch, lease, retries and retention, rate limits, `customers.erasure_delay`, `auth.locked_accounts` (staff logins that can't change their own name, password, two factor or other sessions, `403 account_locked`, and see only their own session: a public demo's shared login; `hypha_users::StaffSettings`), `[agents]`: `enabled`, `writes`, `proposal_lifetime`, `preview_token_lifetime`, `preview_timeout`) live in `hypha.config.toml` (`HYPHA_CONFIG` names another file; without one, every default), typed for editors by `hypha.config.schema.json` (start the file with `#:schema ./hypha.config.schema.json`). Secrets and first-start values stay environment-only (`DATABASE_URL`, `HYPHA_SECRET_KEY`, `HYPHA_S3_ACCESS_KEY_ID`/`_SECRET_ACCESS_KEY`, `HYPHA_SMTP_PASSWORD`, `HYPHA_RESEND_API_KEY`, `HYPHA_OWNER_*`, `HYPHA_STORE_NAME`); `HYPHA_AGENT_WRITES` sets `agents.writes`; the variables that predate the file (`HYPHA_BIND`/`PORT`, `HYPHA_TRUSTED_PROXIES`, `HYPHA_ADMIN_URL`, `HYPHA_ALLOW_PRIVATE_CALLBACKS`, `HYPHA_MEDIA_*`, `HYPHA_S3_ENDPOINT`/`_REGION`/`_BUCKET`/`_CREATE_BUCKET`) still work and win over it, as do `[email]`'s (design note 0028: `HYPHA_EMAIL_SENDER`, `HYPHA_EMAIL_FROM`, `HYPHA_SMTP_HOST`/`_PORT`/`_TLS`, which `.cargo/config.toml` points at the compose Mailpit with: every email of a `cargo run` lands in http://localhost:8025). `cargo run -p hypha-host-axum -- config` prints the settings in effect (`config rate-limits`: the Worker's Rate Limiting bindings as JSON, named, slotted and sized by `Rule`); after changing `hypha-config`'s file types, `cargo run -p hypha-host-axum -- config schema` rewrites the schema (committed; a test fails while it's stale). Key names are a contract with operators: never rename one.
- OpenAPI (design note 0010): after changing routes or DTOs, `cargo run -p hypha-host-axum -- openapi` rewrites `openapi/admin.json`, `openapi/storefront.json` and `openapi/extensions.json` (design note 0029: every extension point as an OpenAPI 3.1 `webhooks` entry keyed by its name, with `x-hypha-extension: {point, version}`, the request body and the 200 answer) (committed; a test fails while they're stale). The running host also serves them at `/admin/openapi.json` and `/storefront/openapi.json`.
- End-to-end check against a freshly started host on a fresh database (Git Bash on Windows; the script reuses handles and countries): `docker compose exec -T postgres psql -U hypha -c "DROP DATABASE IF EXISTS hypha_e2e" -c "CREATE DATABASE hypha_e2e"`, then start the host through cargo (`cargo run -p hypha-host-axum`, so `.cargo/config.toml`'s `HYPHA_S3_*` point it at the compose S3 server) with `DATABASE_URL=postgres://hypha:hypha@localhost:5432/hypha_e2e`, a `HYPHA_SECRET_KEY` `HYPHA_OWNER_EMAIL=owner@example.com HYPHA_OWNER_PASSWORD=e2e-owner-password` (the script logs in as that owner) and `HYPHA_ALLOW_PRIVATE_CALLBACKS=true` (its webhook receiver listens on localhost, with python3, and serves the OAuth steps' app manifest) and `HYPHA_ADMIN_URL=http://admin.e2e.test` (the consent page `/oauth/authorize` sends to; the script plays the admin), and run `bash scripts/e2e.sh` (`HYPHA_URL` for another port). Asserts status + error `code` per step, exits non-zero on failure. When the host sends over SMTP (a `cargo run` does, to the compose Mailpit) and Mailpit's API answers at `MAILPIT_URL` (default http://localhost:8025), it also checks the order and invite emails arrived there and deletes them; with another sender (the log, as on Workers) or `E2E_MAILPIT=0` it skips those. Run it after changing routes, DTOs or error mapping, and add a step for new routes.
- The API on Workers (design note 0026, `crates/hypha-host-workers`): the same routes over Hyperdrive, with an isolate's state (config, secret key, store, key cache, limiter counts, routes) kept between requests and an `AppState` per request (its `waitUntil`). It runs no migrations and creates no store: set the database up first with the native host's `setup` (W9: migrations, the store, the owner, the default location, the search index, then it exits: `DATABASE_URL=…/hypha_workers HYPHA_SECRET_KEY=… HYPHA_OWNER_EMAIL=… HYPHA_OWNER_PASSWORD=… cargo run -p hypha-host-axum -- setup`; a reset database needs a restarted Worker, since the isolate keeps the store's ID). Copy `.dev.vars.example` to `.dev.vars` with the same key, then `wrangler dev --port 3989` in that folder (`localConnectionString` points at the compose `hypha_workers` database) and `HYPHA_URL=http://localhost:3989 bash scripts/e2e.sh`. One cron a minute runs dispatch and search sync when the `JOBS` KV namespace's marks say there's work (W7, `marks.rs`: `written` when a run left work, `checked` when a tick's run left none, `due` from `OutboxRepo::next_due`; an hourly tick runs them regardless), so a quiet store's ticks don't touch Postgres, and the other jobs on the ticks that start their `jobs.<job>.interval` (`curl "http://localhost:3989/cdn-cgi/handler/scheduled?cron=*+*+*+*+*"` triggers one locally); a write that committed events (or retried a delivery) runs dispatch and search sync in `waitUntil`, starting no delivery that couldn't finish within its 30 seconds (`jobs::dispatch_by`). One `AppState` and router per isolate; an event's `waitUntil` and write flag reach them through `Scoped` (the event is current while its future is polled). Its Hyperdrive must be created with `--caching-disabled`: the API's reads outside transactions (sessions, keys) must not be served from a cache. From our own Workers (through a Service Binding, sending the deployment's `HYPHA_CALLER_KEY` as `X-Hypha-Caller`; not the binding's props, which Cloudflare drops for a Worker with a placement), the client's address is the caller's `X-Forwarded-For`, otherwise `CF-Connecting-IP` (`peer.rs`). Its `ids` (UUIDv7 in order within a millisecond), `limiter` (W8: each check counts in the isolate, GCRA with the quota's exact shape, then on the rule's Rate Limiting binding (`Rule::binding`, `binding_slot`, `binding_limit` in `hypha-http`), which caps all isolates together at the most the quota allows in a minute; `wrangler.toml`'s bindings are the defaults', a test keeps them in step), `marks` and `schedule` are portable and tested natively.
- Postgres (Docker Desktop): `docker compose up -d`; `cargo nextest run -p hypha-store-postgres` runs the repository contract against `postgres-test` and `cargo nextest run -p hypha-host-axum` the route tests (each test gets its own database, copied from a template migrated once per set of migrations and dropped after; a changed migration gets a new template; `cargo nextest run -p hypha-http` the HTTP layer's own). `postgres-test` keeps nothing across restarts: never point anything worth keeping at it.

## TypeScript apps (design note 0011)

`status`, `logs [service]`. `--target local` runs it on this machine under `*.hypha.localhost`. `--target cloudflare` (design note 0026, §5; `src/cloudflare.ts`) deploys the API, the admin and the storefront as Workers, the API over Hyperdrive to any Postgres given by its direct URL, all with one Cloudflare API token (`CLOUDFLARE_API_TOKEN` in the deployment's `.env`, passed to wrangler and `cf`, so neither tool's own login decides the account; Emails link to `/order/<id>?token=` (the `order_url` pattern `https://<storefront>/order/{order}?token={token}`, set by `hypha deploy` when it connects the storefront unless the store has one, and by `pnpm seed`): a route handler (`app/order/[id]/route.ts`; country-less, the proxy lets it through in both routing modes) checks the token, keeps it in that cookie and redirects to the order's country's confirmation without it; a wrong token lands there without one. Pages live under `app/[country]/(shop)/`: `[country]` is the URL's locale segment, `/{country}` in the market's default language and `/{language}-{country}` in another (`/de`, `/en-de`, `/sr-latn-rs`: the last part is the country; in a single tree no prefix for the default and `/{language}` for another, rewritten by the proxy to the folder form), all of it parsed in `lib/routing.ts` (pure, tested: `localeOfSegment`, `canonicalSegment`, `href`, `routeFor`, `alternatePlaces`) on the i18n package's `parseLocaleSegment`/`formatLocaleSegment`. `app/[country]/layout.tsx` is the root layout (the document's `lang`/`dir` follow the segment; `next.config.ts`' `experimental.globalNotFound` with `app/global-not-found.tsx` for paths outside a place), `(shop)/layout.tsx` the header and footer and the 404 for a country nobody sells to. `proxy.ts` picks the country (folders by default, `STOREFRONT_ROUTING=single` for one tree) and, only for a bare path, the language (the `language` cookie the switcher sets, then `Accept-Language` matched against the country's `languages`, then its default); a segment naming a language the country doesn't offer is redirected to the one it comes to (`de-at` → `de`, `en-gb` → `en`), else the country's default URL; a URL naming a language is never redirected by a cookie or a header. Links go through `lib/site.ts`'s `link(segment, path)`, given the page's segment (`params.country`) so they keep its language; client components and server actions get it from `components/locale.tsx` (`useLocale()`: every action takes `locale`, the segment, and reads the country and language from it again with `pageLocale`). The header's language switcher (`components/language-switcher.tsx`, shown with more than one language, names in themselves) keeps the page and its query. Cached reads put the language in their keys (`["product", handle, country, language]`, `store`, `categories`, `category`, `custom-field-definitions`), tags stay per resource; the webhook expires them on `translation.*` (by `data.resource.kind`, `lib/cache-tags.ts`' `languageChange`) and `store.updated`. SEO: `hreflang` for every (language, country) pair as `de-CH` plus `x-default`, the page's own URL canonical, `og:locale`, JSON-LD `inLanguage`, the sitemap and robots per place. Not in the page's language yet (the API owes them): search results, carts and orders. Money uses each country's minor units from `/storefront/countries`. It's built from Astryx components (only interactive parts are client components) with its own theme, `apps/storefront/theme/shopTheme.ts`: after editing it, `pnpm --filter storefront theme:build` (built `shop.css` / `shop.js` committed; `theme:check` fails while stale). A listing's state (words, facets, price, sort, the page and the pages before it) lives in its URL (`lib/listing.ts`); its controls change the URL in place (`history.pushState`, `components/listing-controls.tsx`'s `go`), so nothing is re-rendered on the server and only the results are read again, dimmed meanwhile; the facet column and the header's categories are responsive by CSS (`globals.css`), never by a JS media query, so the HTML is the same at every width. A header category with subcategories is `components/nav-menu.tsx`: the category's link plus a chevron button (`aria-expanded`) disclosing the panel, one open at a time (the header holds which), opened by hover intent or click, closed on Escape, focus leaving or a click elsewhere. Every link is `components/site-link.tsx` (Next's, through Astryx's `LinkProvider`): it starts the top navigation bar (`components/navigation-progress.tsx`, ended by the page change; `useNavigationProgress().start()` before a `router.push` or an action that redirects). Product cards are their own `next/link` anchors (`components/product-grid.tsx`), so Next prefetches them in the viewport; Astryx's `ClickableCard` hides its link in a 1px element that the viewport prefetch never sees, so don't use it for navigation. Page changes, a listing's result changes and the product hero animate with React's `ViewTransition` (`components/page-transition.tsx`, `product-grid.tsx`, the product form; the classes are in `globals.css`): import it and `addTransitionType` from `components/view-transition.tsx`, never from "react" directly (vinext rewrites such an import to a shim that drops the statement's other exports in dev); the page's boundary is keyed by the path (`components/page-transition.tsx`: only a navigation enters and exits; anything else in a transition, a sheet opened by an Astryx button, whose clicks run in transitions, the cart, is an update and `none`, or the whole page cross-fades and flickers), a transition within a page still adds the `WITHIN_PAGE` type, drawers and sheets are imported with their component, never `lazy` (a Suspense reveal is animated too), and the hero cross-fades only on `HERO_IMAGE`, since any re-render inside a boundary counts as an update; a product's image is the shared element between its card (`shared` on `ProductGrid`, only where a product appears once) and its page.

Astryx's own strings come from its shipped catalog for the language (`lib/astryx-messages.ts`: only the parts the shop's components read, `PARTS`; Serbian through the package's `serbianLatin`, since Astryx ships Cyrillic). Client components call `useT()` (`lib/use-t.ts`), typed with the namespaces every page is sent (`SHARED_NAMESPACES`: common, header, cart, discounts, product, listing; `ClientMessages` in the country layout); checkout and the account send theirs from a layout of their own and their forms ask for them (`useT<"checkout" | "address">()`), so a key whose namespace the page wasn't sent doesn't compile (and warns in development if it's read anyway) and no page gets the whole catalog. Components and helpers shared by servers and browsers take the translator as `t` (`Price`, `Totals`, `ProductGrid`, `lib/discounts.ts`, `lib/prices.ts`). Every format takes the translator's `locale`, `localeOf(language, country)`, through the package's `withEnglish` (`formatMoney(money, digits, t.locale)`, `lib/format.ts`'s `formatDate` and `countryName`): never a literal `"en"`. Literal text in JSX (between tags and in `label`/`title`/`description`/`placeholder`/`alt`/`aria-label`) fails `pnpm lint` (`i18n/no-literal-text`, `scripts/oxlint-i18n.mjs`); a message's tags are functions (`t.rich(key, { link: (chunks, key) => <a key={key}>…</a> })`), plurals and values ICU, never concatenation.

## Architecture (hexagonal / ports and adapters)

Dependencies point inward: hosts → domain crates → core. Core and domain crates never depend on storage, HTTP or runtimes.

Domain crates are layered; a crate may only depend on layers below it (Cargo rejects cycles, so a wrong edge forces a painful restructure later):

| Layer | Crates | May depend on |
| --- | --- | --- |
| Hosts | `hypha-host-axum` (a library plus `host! { spores: [...] }`, and the stock binary: startup, config, migrations, serving), `hypha-host-workers` (`worker! { spores: [...] }`) on `hypha-http` (the routes, extractors, errors, DTOs, OpenAPI and host state; design note 0026, W3) | anything |
| Spores | `hypha-spore-core` (design note 0030: `Spore`, `SporeSet`, `SporeEnv`, `SporeUi`, `SporeRuntime`: what hosts list and `hypha-http` asks), `hypha-spore` (the facade spores depend on, SP6) | storage adapters, workflows, domain crates, core (`hypha-spore`'s `http` feature: `hypha-http`); only hosts (`hypha-http` included) and spores depend on them |
| Storage adapters | `hypha-store-postgres` (tokio-postgres; native and Workers via Hyperdrive), `hypha-store-s3` (files over the S3 API: R2, S3; HTTP through its `HttpClient` port) | domain crates, core (and `hypha-promotions`, whose engine they name as their `HasPromotions`); never hosts |
| Protocols | `hypha-mcp` (the MCP server for admin agents: JSON-RPC, versions, tools, behind its `Operations` port; knows no routes, storage or grants) | core only; only `hypha-http` depends on it |
| Configuration | `hypha-config` (design note 0017: `hypha.config.toml` into each crate's settings; parses a string, so it builds for wasm) | workflows, domain crates, core; only hosts depend on it |
| Workflows | `hypha-checkout` (cart → order and its payment, choosing a payment method, the cart's messages and `checkout_blocked`, the one workflow on `hypha-checkout-rules`; design notes 0027, 0040), `hypha-promotions` (the cart's `Promotions` port on `hypha-discounts`: reads what a cart's discounts are weighed with, runs the engine on the lines the cart hands over, maps the outcome back), `hypha-order-actions` (fulfil, cancel a fulfilment, cancel an order, record money received: orders, fulfilments, payments and stock in one batch; design notes 0018, 0027), `hypha-dispatch` (delivering domain events: fan-out, retries, webhooks to apps through the host's `WebhookSender` port, and the in-process handlers the host passes it; design note 0016), `hypha-search` (building search documents per market, the `SearchIndexer` handler, the sync job, searching a shopper's market; design note 0019), `hypha-mail` (emails: each template's context from orders, fulfilments, payments, purchase orders, the store and media, the `Mailer` handler, previews, test sends, resends, the staff flows' emails; design note 0028), `hypha-privacy` (personal data over customers: deleting one without orders, erasing one with them, data export; design note 0032 §7), `hypha-receiving` (goods arriving against purchase orders: the order's counts, the receipt and the stock with its cost in one batch; design note 0039) | composing and leaf domains, core |
| Composing domains | `hypha-cart`, `hypha-users`, `hypha-customer-accounts`, `hypha-merchandising`, `hypha-oauth` | leaf domains, core (`hypha-users` → `hypha-auth` only; `hypha-customer-accounts` → `hypha-auth`, `hypha-customers`, `hypha-cart`; `hypha-merchandising` → `hypha-products`, `hypha-media`, `hypha-categories` only: a category's image, design note 0022 Q5; `hypha-oauth` → `hypha-apps`, `hypha-auth` only) |
| Leaf domains | `hypha-addresses`, `hypha-products`, `hypha-markets`, `hypha-pricing`, `hypha-tax`, `hypha-inventory`, `hypha-customers`, `hypha-stores`, `hypha-orders`, `hypha-fulfillment`, `hypha-payments`, `hypha-auth`, `hypha-media`, `hypha-shipping`, `hypha-apps`, `hypha-search-index`, `hypha-channels`, `hypha-categories`, `hypha-custom-fields`, `hypha-notifications`, `hypha-extensions`, `hypha-agents`, `hypha-discounts`, `hypha-purchasing`, `hypha-checkout-rules`, `hypha-translations` | core; `hypha-pricing` → `hypha-markets` only |
| Core | `hypha-core` | nothing internal |

Leaf functions take the plain values they need (IDs, `Price`), not another leaf's aggregate. E.g. `resolve_price` takes `ProductId`, `VariantId` and the base `Price` rather than `&Product`; the composing command (cart) loads the product and passes them in. Ask before adding a new edge between domain crates.

- `hypha-core`: shared types only — `Money`/`Price`/`BasisPoints` (`money/`), prefixed IDs (`ids.rs`), `CountryCode`, `Email`, `Address`, `Scope`, `Ctx`/`Actor`, generic ports (`IdGenerator`, `Clock`, `HasBatch`, `RepoError` in `ports.rs`), `Timestamp` (`time.rs`, µs since the epoch), list pages (`page.rs`: `PageRequest`/`Page`, newest first by UUIDv7 ID; hosts expose an opaque `cursor`, design note 0012; a sorted list (design note 0024) takes `PageRequest<Keyset<Id>>`, the last item's `SortKey` with its ID, its order a domain enum like `ProductSort` that adapters map to `ORDER BY key, id` with an index per key, and its route parses with `ListQuery::parse_sorted` (filters implement `SortedFilters`) and answers with `PageResponse::sorted`; a repo's `list` returns the domain's summary read model, e.g. `ProductSummary` from `Product::summary`, which adapters may compute in storage), idempotency keys (`idempotency.rs`: a keyed command checks `earlier_result` first, then stages an `IdempotencyRecord` in the same batch as its write, and after *any* failed keyed write looks the key up again and replays the winner, since a racing request with the same key can fail it on the cart or order before the key; see `hypha-cart`'s `write_cart` and `hypha-checkout`'s retry loop). No domain logic, no I/O.
- Domain crates (`hypha-products`, `hypha-markets`, `hypha-pricing`, `hypha-tax`, `hypha-inventory`, `hypha-customers`, `hypha-orders`, `hypha-cart`, and the `hypha-checkout` workflow): aggregates with private fields and validated constructors, a repository trait (port) per aggregate in `repo.rs`, error enums in `error.rs` (a crate's `CommandError` sits in `commands.rs`), and commands in `commands.rs` (`hypha-products` is the simplest template; `hypha-cart` shows a command that composes several domains; `hypha-checkout` writes several aggregates in one batch and retries when it loses a race).
- `hypha-addresses` (design note 0040): each country's address format, generated from a snapshot of Shopify's `worldwide` data (MIT with Unicode CLDR, `src/generated/LICENSE.md`) by `node scripts/address-data.mjs <worldwide checkout>` (reads its YAML only; writes `src/generated/countries.rs` with the commit read; run by hand to take an update, review the diff): per country the form's rows (`format.edit`), labels (English, the country's `en.yml` over the defaults), how it uses postal codes (`PostalCode`: none, required, recommended, optional, by worldwide's own rule), the postal code pattern rewritten for the `regex` crate (`\d` → `[0-9]`, a lookahead → `postal_exclude`; anything else stops the script), regions (code, name, alternates, postal code prefixes) where the form shows the region, and whether a house number is expected. `Formats` implements core's `AddressFormats` port (`check`: normalises, the region's name/alternate/code to its code case-insensitively and the postal code upper-cased with spaces collapsed, dropped where the country has none; problems `required`/`unknown_region`/`invalid_format` (with the example)/`region_mismatch` (by prefixes, only when the data places the code); the `house_number_missing` warning; `AddressFlags` (`po_box`, `military`, `parcel_locker`, `non_latin`, `flags.rs`)). Core's provided `AddressFormats::validate(parts)` is what every write of an address goes through (carts' shipping address, customers' address books on both surfaces, locations): `Address::new`'s rules and the country's together, refusing `AddressError::Invalid` with every problem (`422 invalid_address`, `details.problems: [{field, code, message, params}]`, filled by `error.rs`'s `address_problems` for every domain whose error carries an `AddressError`); `Address::new` alone stays the structural check (stores' legal address, suppliers) and restoring a stored address never runs the format, so rows written before still load. Commands take `formats: &impl AddressFormats`; hosts pass `&hypha_addresses::Formats` (static data, compiled patterns cached per country on first use) and tests the same (a dev-dependency). An `Agent` is `Connected { user }` (a staff member connected an MCP client, `AgentClient`: its metadata document's URL and name; it acts for them, capped by their role at every request) or `Autonomous` (staff's, for a job); `enabled`, `last_used_at` (written apart by `AgentRepo::record_use`, at most once per `USE_RESOLUTION`, no version or event), `revoked_at` (for good); events `agent.created`, `agent.updated` (one per write, listing what changed), `agent.revoked`. Its `Grant` holds read scopes, write scopes each with a `WriteMode` (`Propose` or `Apply`), `customer_data:*` scopes and an optional allowlist of `OperationId`s (the OpenAPI `operationId`s, `admin.products.update`); `NEVER_GRANTED` (`checkout`, `users:write`, `api_keys:write`, `apps:write`, `agents:write`) and `PROPOSE_ONLY` (`customers:erase`, `purchasing:send`) are fixed in code, and a scope in the wrong list is refused by name (`agent_scope_not_grantable`, `invalid_grant`). `effective(grant, cap, role)` is what a grant comes to at a request: reads include those its writes imply, everything within the person's role (`None` for an autonomous agent), writes under the operator's `WritesCap` (`Propose` turns `Apply` into `Propose`, `Off` drops them); `mode_for(scopes)` is how a write may go, decided by the write scopes held alone (any held only to propose: `Propose`; a scope missing never makes a direct write), `holds_all(scopes)` whether it may call it at all; a direct read or write runs with `Permissions::applied_scopes()` (no write scope held only to propose, so such a write can't commit there by construction), previews, proposals and approved proposals with `scopes()`. Granting (`require_grantable`): nobody grants a scope they lack, and only a staff session grants `Apply`; `update_agent` lets a caller without the whole grant only narrow the allowlist (widening or lifting it hands the grant out again). Credentials are `hypha-auth`'s: `prepare_autonomous_agent` / `prepare_connected_agent` check and build an agent for a workflow that stages it (`StageAgents`) with its token; the host checks `active_agent` (`agent_revoked`, `agent_disabled`) per request. A `Proposal` (`prop_…`) is a write an agent previewed and left for a person (operation, the `ProposalRequest` to replay, idempotency key (one per agent, `PROPOSAL_KEY`: a retry answers the first), the preview as opaque JSON, its digest, the scopes it needs, `expires_at` from `AgentSettings::proposal_lifetime`); `Pending` moves to `Applying` when approved (`start_applying`: approver and time in `decided_by`/`decided_at`; nobody else decides it meanwhile, `proposal_applying`; past `APPLYING_LEASE` it counts as pending again), `Rejected` (with a note) or `Expired` (`expire_proposals`, a job step); `Applying` moves to `Applied`/`Failed` (with the `ProposalResponse`) or back to `Pending` (`release`, `refresh`); events `proposal.created`, `proposal.decided`. `create_proposal` takes the agent from the context, never input; `approve_proposal` (a staff session holding every scope, open, not expired, the agent active, `refreshes` as the approver saw it or `proposal_changed`) claims it (`applying`, version-checked) and returns it for the host to apply, which then calls `record_applied` / `record_failed` / `record_refreshed` / `release_proposal`; an agent reads only its own proposals (`get_proposal`, `list_proposals`; `approvable` lists what the caller could approve). `AgentCall` (`acall_…`, `agent_calls`) logs every tool call (operation, `CallMode`, status, error code, duration; no bodies), pruned by `prune_agent_calls` (`AgentSettings::keep_calls`). Tables in `0067_agents.sql`.
- `hypha-discounts` (design note 0038): discounts (`disc_…`), automatic or by code, as typed data: `conditions` (markets, channels, customer groups, customers, signed in, minimum subtotal per market, minimum quantity; all must hold), a `Kind` (`Standard` with 1 to 3 rewards, one per class: a `Target` (items as an `ItemSet` with `exclude_on_sale`, the subtotal, shipping with an optional cap) and a `Value` (percent in basis points, an amount per market spread `each`/`across`/`cheapest`, a fixed price per unit); `BuyXGetY`; `Tiered`), `combines_with` classes (two apply together only when each allows every class of the other) and `Limits` (total uses, once per customer). Codes are rows of their own keyed by `normalize` (trimmed, NFKC, upper-cased; unique in the store), generated from an alphabet without look-alikes. `summary()` is the one sentence every surface shows. The engine (`engine.rs`, `apply(input, candidates) -> Outcome`) is pure: product rewards on each line's base, added up and clipped (percentages, amounts, fixed prices, by ID) at the base; order rewards on the subtotal after product rewards, spread by largest remainder over what each line has left; one shipping reward on the chosen option's rate for the discounted subtotal (the cart passes the rate as a function); the best set by seeding each candidate and adding the rest greedily; every code the cart holds gets a `CodeState`. `DiscountContext::load` reads what a cart weighs (live automatic discounts, the cart's codes, usage counts, the buyer's once-per-customer uses). Usage is counted only in checkout's batch (`StageDiscounts::claim_discount_usage`: a conditional increment of `discount_usage_counts` and of the code's `used`, `Duplicate(DISCOUNT_USAGE_LIMIT)` past a limit; a usage row unique per (discount, customer) when once per customer, `Duplicate(DISCOUNT_PER_CUSTOMER)`). At most `MAX_LIVE_AUTOMATIC` (100) automatic discounts are active and not expired (`409 too_many_automatic_discounts`). Routes in `hypha-http`'s `routes/discounts.rs`; tables in `0083_discounts.sql`. Offers show `amount_after_discounts` (`shipping_after_discounts`). Orders keep `discounts` (`OrderDiscount`: copies of each applied reward, its value and target as the leaf's JSON, `hypha_discounts::json`) and `discount_total`; each `OrderLine` has `subtotal` (unit × quantity), `discounts` (`DiscountShare`) and `total` = subtotal − shares (what tax and refunds go by), each `OrderShippingLine` `amount`, `discounts`, `total`; `restore` holds every share to a listed discount and each discount to the sum of its shares (`discounts_mismatch`), migration 0085 (old rows: subtotal = total, no discounts). Checkout copies them and stages one `UsageClaim` per discount in the order's batch (the customer it resolved; each application carries `once_per_customer` and its code's limit, so checkout needs only the leaf's `StageDiscounts`); a claim refused (`DISCOUNT_USAGE_LIMIT`, `DISCOUNT_PER_CUSTOMER`) is `409 discounts_changed` with the cart's total and codes now, nothing placed, money given back like `total_changed`. `order.placed` gains `discount_codes` and `discount_total`; the order emails' context gains `order.discounts[]` (`title`, `code`, `summary`, `amount`), `order.discount_total` and each line's `original_total` and `discount`. - `hypha-mcp` (design note 0035, "As built: hypha-mcp"): the MCP server as a pure library (serde, core; wasm-clean, no I/O). `Server::new(ServerConfig)` (name, version, instructions (none unless the host gives them), the curated `direct_tools` as `OperationId`s (core's, shared with `hypha-agents`: lowercase dot-separated segments, at least two, at most 128 bytes, no `__` nor an `_` ending a segment, so `tool_name()` (each `.` as `__`) reads back through `from_tool_name`; `invalid_operation_id`)), then `server.handle(&ops, McpRequest { body, headers })` → `McpResponse { status, body }` per POST: the transport only authenticates, checks `Origin`, answers `405` to GET/DELETE and sends `application/json` (none on `202`). - Agents (design note 0035; `hypha-agents` the leaf, `hypha-http`'s `agents.rs`, `operations.rs`, `internal.rs`, `routes/agents.rs`): admin agents (`agent_…`, `Actor::Agent`), connected (a staff member's MCP client, capped by their role read fresh at every call; connecting needs only their session) or autonomous (staff make one with `agents:write`, `POST /admin/agents`, its key `hypha_ak_…` shown once: an `Identity` with `Principal::Agent` and `Credential::AgentKey`, looked up by its hash). Proposals and call log items carry their operation's `summary`; a proposal's `request`, `preview` and `response` are shown to a caller other than a staff session only when it holds every scope the write takes and every `customer_data:*` scope (else absent and listed in `redacted`), the proposing agent included; grant errors answer `details: {field, scope?, operation?}` (`GrantError::field`). The prune job expires proposals (`agents.proposal_lifetime`), prunes agent calls (`jobs.prune.agent_calls_after`) and expired preview tokens.

- Applying a preview (`preview.rs`): a complete preview answers `token` (`hypha_pv_…`, stored as SHA-256 in `preview_tokens`, `agents.preview_token_lifetime`) and `expires_at`, bound to the caller and the request's fingerprint (`extract::fingerprint`: method, path, query, canonical body), with the IDs it was handed and its digest (`preview::digest` over the `WriteRecord` its store read back: the events (type, version, subject, data with times blanked: RFC 3339 strings, and numbers under a key ending in `_at`) and the rows of aggregates written, each with the version found: the `hypha_note_write` trigger on every table with a bigint `version` (migration 0073, firing only while logging; a test holds new tables to it, logging into the transaction-local `hypha.writes` while `hypha.log_writes` is on, so a write over a record changed since the preview differs even when its events don't). An answer that replays its `Idempotency-Key` is answered as is. Its effects outside the database follow the same rule: emails and background work are held (`Run::hold_email`, `defer`) and run after the COMMIT, dropped on a rollback; calls out go only to read-only extension points (as its complete preview could), and anything else (another call, media storage, an upload URL) is blocked before it goes out and the apply is stale (`blocked_by` in the fresh preview).
- Personal data (design note 0029, AP10): `hypha-http`'s `redact.rs` is the one place that decides it. - `hypha-http` and `hypha-host-axum` (design note 0026, W3): `hypha-http` is the HTTP layer as a library that builds for wasm (routes, extractors, errors, DTOs, OpenAPI, `AppState`, the job steps in `jobs.rs`); what only a runtime can do comes from the host through `host.rs`'s capabilities (`HostClock`, `HostIds`, `HostRandom`, `Offload` for CPU-heavy work, `HostBackground`, `HostLimiter`, `HostCalls` for merchant URLs, `HostHttp` for the media storage, `HostMail` for email (`email::LogSender` is the portable `log` sender; SMTP is the native host's `email.rs`, Resend `hypha-mail-resend`), `AfterWrites`), each a shared function with boxed `Send` futures, and the client's address from the host-set `client_ip::PeerAddr`. `hypha-host-axum` is the native host, a library plus a macro (design note 0030, §9): `lib.rs` (the `Deployment` trait; `host! { spores: [...] }` and `deployment!`, which expand the router and the dispatch job with the concrete spore types, for `Send`; `migrations::<D>()`, core's then the spores'), `main.rs` (the stock binary: `hypha_host_axum::host! { spores: [] }`), `start.rs` (the subcommands, startup, config, serving, generic over the `Deployment`; registers each spore's app after migrations and refuses spores that clash), `storage.rs` (`PgDatabase`: the deadpool pool with statement caches, migrated; `PgStorage`: it and the handlers built at startup), `runner.rs` (the job runner and its wake-ups), `limiter.rs` (`governor`), `calls.rs` (`reqwest` with the public-address resolver), `platform.rs` (system clock, UUIDv7, OS randomness, blocking threads, background slots), and the route tests (`route_tests.rs`; they send with a recording `HostMail`, `TestApp::emails`, never the configured sender, so they need no SMTP server). Routes are listed once, in the `route_table!` macro in `routes/mod.rs` (`[surface, METHOD, "/path", module::handler]`): it builds the router per concrete storage (axum can only prove handler futures `Send` for concrete types) and the OpenAPI documents (`routes/openapi.rs`). There are two API surfaces (design note 0010): `/admin/*` (staff sessions and secret keys) and `/storefront/*` (publishable keys), each with its own DTOs where they differ (a storefront never sees drafts or admin fields). A new route is a table row plus a handler with `#[utoipa::path(...)]` (method and path as in the table, `params`, `request_body`, the success response, and `extensions(("x-hypha-scopes" = json!([...])))`) and `utoipa::ToSchema` on its DTOs; operation IDs, tags, security and the standard error responses are added from the table. Without the annotation the table doesn't compile. Every handler takes a `Caller` (`Caller<Admin>`, the default, or `Caller<Storefront>`; the wrong kind of credential for the surface is a 403 before any lookup) (`extract.rs`), the one place a request becomes a `Ctx`: the extractor only reads `Authorization: Bearer` (a staff session `hypha_sess_…`, the role's scopes read fresh each request, or an API key `hypha_sk_…` / `hypha_pk_…`) or `X-Publishable-Key` (none is 401 `unauthenticated`), and the handler's first line is `let (ports, ctx) = caller.authenticate(&state).await?;` (a bad token is 401 `invalid_token`): one pooled connection per request, and the only way to ports besides `state.public_ports()`, which is for routes that need no credentials. Parse bodies only after that: `JsonBody` and `KeyedJson` buffer the bytes, and `body.parse()?` / `req.parse()?` come after `authenticate`, so strangers get a 401 before any JSON work. `/me` routes take `StaffCaller` the same way (API keys get 401 `session_required`). The public routes (login, MFA, password reset, invite acceptance) take a `ClientIp` (`client_ip.rs`) and call `rate_limit::enforce(&state.limiter, Rule::…, key)` per address before parsing and per email after (`429 rate_limited` with `Retry-After`); every limit is a `Rule` with its quota in `rate_limit.rs`, behind the `RateLimiter` port (in memory natively (`limiter.rs`), the Rate Limiting binding on Workers). Work that must outlive the response runs in `state.background` (natively a few slots, drained on shutdown; `waitUntil` on Workers), spawned per concrete storage (`Storage::spawn_password_reset`) for the same `Send` reason as `router!`. Timed work (delivering events, pruning, the media sweep) is `hypha-http`'s steps in `jobs.rs`, run natively by `runner.rs` (started in `serve`, stopped on shutdown; an idle job backs off to `jobs.idle_interval`; `AfterWrites` wakes the dispatcher when a request's ports commit events or retry a delivery (`hypha_core::SignalsDispatch`, set in `AppState::public_ports`), and a dispatch step that did work wakes search sync); each job is a step from a domain crate (`hypha_dispatch::fan_out`, …) that says whether there's more, so a Workers host can call the same steps from a Cron trigger. `HostEnv` (`state.rs`) provides randomness and Argon2id through the host's `Runtime` (`Offload`: blocking threads natively), the `SecretBox` under `HYPHA_SECRET_KEY`, and orders' access tokens (`OrderTokens`, shared with `MailHost` for the emails' links); the staff flows' emails go through `StaffEnv` (`mail.rs`). The router for a concrete storage is `hypha_http::router!(PgStorage)` (handlers and their DTO types are `pub` so it can expand in the host's crate).

Command shape (see `crates/hypha-products/src/commands.rs`): `async fn cmd(ctx: &Ctx, repo: &impl Repo, ids: &impl IdGenerator, input: RawInput) -> Result<_, CommandError>`; first line `ctx.require(Scope::...)?`, then validate raw input through domain constructors. `CommandError` composes lower errors via `#[from]`.

When a command needs more than one repository, take `ports: &S` bound on the accessor traits it uses: each crate defines `HasXxx` (associated repo type + `fn xxx(&self)`) next to its repo traits in `repo.rs`, e.g. `create_cart<S: HasMarkets + HasCarts>`. A composing crate names its union with a blanket impl (`CartPorts`, `PricingPorts` in `crates/hypha-cart/src/commands.rs`), so implementors never list them. Hosts and tests implement the accessors once (`hypha_testkit::InMemoryPorts`, `PgStore`); a new repository adds one `HasXxx`. Static dispatch keeps `Send` provable; don't bundle them into `&dyn` objects.

## Hard constraints

- Core and domain crates must compile for `wasm32-unknown-unknown`: no Tokio, threads, `std::fs`, `SystemTime::now()` or random UUID generation there. Time, IDs and randomness come in through ports.
- Repository traits use `async fn` with `#[allow(async_fn_in_trait)]` and **no `Send` bound**, on purpose (Cloudflare futures are `!Send`). Hosts use concrete types/generics so the compiler can prove `Send`; never `&dyn` for ports used across `.await`.
- Authorization lives in commands (`ctx.require(Scope::...)?`); authentication lives in hosts. Commands never trust raw input.

## Code standards

- Money: integer minor units (`i64`), never floats, capped at ±`Money::MAX_AMOUNT` (2⁵³ − 1) so JSON clients represent every amount exactly; `Money::new` is fallible. Checked arithmetic returning `Result`; percentages as `BasisPoints` with round-half-away-from-zero; `i128` for intermediates.
- Newtypes with validated constructors for anything with rules (`Handle`, `Price`, `CountryCode`, IDs). Don't derive `Deserialize` on validated types unless via `#[serde(try_from = ...)]`.
- IDs: `define_id!` macro in `hypha-core/src/ids.rs` — UUID inside, prefixed string at the edges (`prod_…`, `var_…`, `mkt_…`, `pl_…`). Store native UUIDs; UUIDv7 in hosts.
- Errors: `thiserror` enums with specific variants (no stringly errors). Every error enum implements `hypha_core::ErrorCode` with an exhaustive `match` (no `_` arm): stable snake_case codes, never renamed once released, wrappers delegate to the inner error. Messages use `Display` for domain values (`EUR`, `active`); raw input the caller sent (a string or char that failed to parse) is quoted with `{0:?}`, so blanks and control characters stay visible. No `unwrap`/`expect`/panics in non-test code except documented invariants, each under an `#[expect(clippy::expect_used, reason = "…")]` (or `panic`) naming it; core's codes are pinned in `crates/hypha-core/tests/error_codes.rs`.
- Aggregates own their children (Product owns Variants); cross-aggregate rules live in commands/functions above them.
- Migrations are per module: `hypha_store_postgres::CORE` is core's `MigrationSet`; a spore ships its own set (module `"spore_<name>"`, tables prefixed the same way), passed to `migrate(&mut client, &[CORE, …])`; each new migration of a spore's set is checked against the current schema's catalog before and after (`spore_check.rs`: only `spore_<name>_*` objects, keys into core `ON DELETE CASCADE`/`SET NULL`, nothing on or dropped from core's tables; a breach rolls it back and stops startup). Append only: an applied migration is never edited, renamed or reordered (the runner checks names and fails).
- Postgres queries (design note 0025, §6): repositories take `&impl Queries` (`hypha-store-postgres`'s `store.rs`), never `&impl GenericClient`, and query with `tokio-postgres`'s typed names (`query_typed`, `query_typed_opt`, …) through it: `consistent_read!(conn, |tx| …)` / `in_transaction!` hand out a `Db` with the connection's `StatementCache` (prepared once per pooled connection; none on Workers or with `database.statement_cache = false`), and `conn.db()` outside a transaction. A load with child rows selects them through the root's filter (a join on the root table) and sends its queries together with `try_join*`, pipelined in one round trip, rather than waiting for the root's IDs (see `products.rs`'s `load`).
- Persistence (design note `docs/design/0001-postgres-storage.md`): aggregate roots implement `Versioned`; repos have `insert(&mut T)` / `update(&mut T)`, never an upsert. `update` from an old version fails with `RepoError::StaleVersion`. Uniqueness rules are repo `keys::*` constants reported as `RepoError::Duplicate(key)`; commands keep a read-then-check for precise errors **and** map the `Duplicate` from the write to the same domain error (a race must look like a normal duplicate). In-memory repos are built on `hypha-testkit`'s `Table`, which enforces versions and keys like a database. A command writes one aggregate through its repo, or several through one `HasBatch` commit (`hypha-core/src/ports.rs`): each crate has a `StageXxx` trait next to its repo trait (`StageCarts`), implemented by the adapters' batch types (`InMemoryBatch`, `PgBatch`), and staging moves the aggregate to the version it gets on commit. Stock is reserved in memory by `hypha_inventory::reserve_lines`, and checkout stages the changed items in its own batch. Domain events (design note 0016): an aggregate records them (`hypha_core::Recorded`; a `Recorder`, or a coalescing type like products' `Changes`), and every write of it (repo `insert`/`update`, `Stage*` in a batch) takes them and writes them to `outbox_events` in the same transaction, stamped with the ports' actor (`ActingAs`, set in `Caller::authenticate`); set-based writes (catalog membership, fixed prices, tax-class assignment) are staged in a batch with their events (`StageCatalogProducts`, `StageEvents`, …); the repos' own set-based methods record nothing and are for setting up data. Take an aggregate's events before copying it into a batch, so the stored copy carries none. Aggregate roots also carry `Stamps` (`created_at`/`updated_at`, `hypha_core::Stamped`): adapters set them with `stamp_insert`/`stamp_update` from the ports' clock (`PgStore::new(conn, clock)`; in memory, the shared `InMemoryOutbox`'s fixed clock) before taking the snapshot, in repo writes and when staging. Payloads are contract types in the domain crate's `events.rs` (subject and what changed, not the aggregate; a reshaped field is a new version). `restore` re-runs constructor rules, so tightening a rule (a shorter max length, a newly required field) needs a migration that fixes or rejects existing rows first, or those rows stop loading (500).
- Getters return values for `Copy` types and references (`&str`, slices) for owned heap data.
- Comments say what the code can't: a rule's reason, a contract, a trap. They never cite design notes (no "(design note 0029, §3.1)", "(0013, M6)" or "§5") and don't restate the note's history; the notes are in `docs/design/` for whoever wants the background.
- Workspace lints (`Cargo.toml`, `clippy.toml`): `unsafe_code = "forbid"`, `unreachable_pub`, `clippy::all`, plus panics (`unwrap_used`, `expect_used`, `panic`), casts (`cast_possible_truncation`, `_wrap`, `cast_sign_loss`: convert with `try_from`, or `#[expect]` with why it fits), `trivially_copy_pass_by_ref`, `redundant_clone`, `unused_async`, `unnecessary_wraps`, `manual_let_else`, `semicolon_if_nothing_returned`. Tests may panic and cast: `#[test]` functions by `clippy.toml`, and every `tests/*.rs` file, `hypha-testkit` and the `testing.rs` kits open with `#![allow(…, reason = "…")]` for them (copy it into a new test file). An exception is `#[expect(lint, reason = "…")]` on the narrowest statement or function, so it's flagged once it's stale; `#[allow]` only where the lint fires on one target alone. The Workers host has wasm-only code: CI also runs `cargo clippy -p hypha-host-workers --target wasm32-unknown-unknown -- -D warnings`. `cargo shear` (CI) refuses dependencies no code uses. Code must be fmt-clean and clippy-warning-free.

## Testing

- Unit tests in `#[cfg(test)] mod tests` at the bottom of each file; one rule per test; test boundaries (0 vs -1, exact rounding halves); compare expected errors exactly with `assert_eq!(result, Err(...))`, never via `unwrap`.
- Command tests are integration tests in each crate's `tests/` folder using `hypha-testkit` (avoids duplicate-crate issues with dev-dependencies).
- Async in tests via `pollster::block_on`; deterministic IDs via `SequentialIds` and `Uuid::from_u128(n)`; time via `FixedClock` (commands take `clock: &impl Clock` like `ids`).
- Repository contract: `hypha_testkit::contract::{product_repo, product_list, stock_movements, market_repo, catalog_repo, price_list_repo, cart_repo, tax_class_repo, tax_region_repo, location_repo, inventory_item_repo, customer_repo, order_repo, fulfillment_repo, payment_method_repo, payment_method_delete, payment_repo, payment_batch, idempotency_repo, batch, identity_repo, session_repo, api_key_repo, password_reset_repo, user_repo, role_repo, invite_repo, staff_sessions, staff_batch, asset_repo, asset_usages, shipping_zone_repo, app_provider_repo, app_repo, oauth_repos, outbox, search_index, search_queue, search_settings_repo, channel_repo, category_repo, notification_template_repo, notification_settings_repo, notification_repo, notification_settings_batch, custom_field_definitions, custom_field_values, agent_repo, proposal_repo, agent_call_repo, discount_repo, supplier_repo, supplier_variants, purchase_order_repo, receipt_repo, transfer_repo, checkout_rule_repo, translation_repo}` and `blob_store` (file storage: run with the client's upload and download as closures; the S3 adapter runs it against MinIO) define what every repo adapter must do (round trips, versions, unique keys, batched methods). The suite is behind testkit's `contract` feature (so hosts don't ship it): adapters enable it as a dev-dependency, and the in-memory run (`crates/hypha-testkit/tests/contract.rs`) needs `--features contract` when testing that crate alone (`cargo test --workspace` enables it). Every new adapter must run it. Batch methods state caller preconditions (parent exists, no duplicates) in their docs, and the contract checks that breaking them fails. When a repo trait gains a method or a unique key, add a contract scenario first.

## Conventions

- Conventional Commits (`feat(products): …`, `refactor(core): …`); pure moves/refactors in separate commits from features.
- Branches: features are built on `feat/<name>` branches cut from `dev` and merged into `dev`; `dev` is released to `main` (a pull request from `dev`, which CI skips: `dev`'s pushes already ran it). Never commit features straight to `main`.
- LF line endings (enforced by `.gitattributes`). Windows dev machine; prefer cross-platform commands.
