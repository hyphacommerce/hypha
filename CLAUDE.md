# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Hypha (working name): open-source, modular e-commerce API in Rust (edition 2024, Cargo workspace, `crates/*`).
- **Modular**: one crate per domain; behavior is extended through plugins ("spores") via traits and events, not by editing core.
- **Agent-friendly, in two specific ways** (shopping agents are *not* the target of the core API):
  1. **Building Hypha**: the codebase is meant to be easy for coding agents to extend: core, domain crates and plugins ("spores"). Favor explicit types, small crates with clear ports, exact errors and fast deterministic tests over cleverness.
  2. **Admin assistance**: agents will help merchants operate the system from the admin panel. Every operation is a command with typed input, required scopes and typed errors, so the same surface can be exposed over HTTP, MCP and CLI; such agents act as `Actor::Agent` with their own scopes.
  - Agentic *shopping* goes through a separate adapter for the Universal Commerce Protocol (UCP, ucp.dev; planned via ucphub.ai), not through the core commands directly. Design storefront-facing read models (e.g. priced carts) so they map cleanly onto UCP, e.g. per-line problems → UCP `messages` with a `path` to the line.
- **Large catalogs**: sparse explicit variants (never generate the Cartesian product of options); Shopify-style markets / catalogs / price lists.
- **Multi-host**: the same core runs on Cloudflare Workers (WASM), AWS Lambda, Vercel and a plain VPS (axum).
- It's also a Rust learning project for the maintainer (Danilo, TypeScript background). See "Working with Danilo".

## Commands

Run all four before considering work done; CI (`.github/workflows/ci.yml`) runs them too, plus e2e and the TypeScript checks, with clippy warnings as errors (the tests need Postgres: `docker compose up -d`; `.cargo/config.toml` points `DATABASE_URL` at it, and an exported `DATABASE_URL` wins):

```bash
cargo fmt --all
cargo clippy --workspace --all-targets
cargo test --workspace
cargo build -p hypha-core -p hypha-products -p hypha-markets -p hypha-pricing -p hypha-cart -p hypha-tax -p hypha-inventory -p hypha-customers -p hypha-stores -p hypha-orders -p hypha-fulfillment -p hypha-checkout -p hypha-order-actions -p hypha-dispatch -p hypha-auth -p hypha-users -p hypha-media -p hypha-merchandising -p hypha-shipping -p hypha-apps -p hypha-config -p hypha-store-postgres -p hypha-store-s3 --target wasm32-unknown-unknown
```

Extend the wasm build list when a domain crate or storage adapter is added.

- Single crate's tests: `cargo test -p hypha-products`
- Single test by name: `cargo test -p hypha-products rejects_same_handle_products`
- Only an integration test file: `cargo test -p hypha-products --test commands`
- Run the HTTP host (binds `server.bind`, `127.0.0.1:3000` by default; `RUST_LOG` respected; Ctrl+C or SIGTERM drains in-flight requests; `GET /health` for probes): `HYPHA_SECRET_KEY=… cargo run -p hypha-host-axum`, on Postgres only (`DATABASE_URL`, the compose database by default under cargo; migrations run on startup). `HYPHA_SECRET_KEY` is 64 hex characters from `openssl rand -hex 32`, kept across restarts since it seals 2FA secrets. Every route but `/health` and the login ones needs credentials (design note 0008): on first start, `HYPHA_OWNER_EMAIL` and `HYPHA_OWNER_PASSWORD` create the owner, who logs in with `POST /auth/login`. Emails (invites, resets) are logged, not sent; `server.admin_url` turns their tokens into links. The public routes are rate limited per client address (design note 0009): behind a proxy or load balancer, set `server.trusted_proxies` (CIDR ranges) so `X-Forwarded-For` is believed from those peers, or every client shares one limit (a server-rendered storefront is such a proxy: it passes shoppers' addresses). Calls to merchant-configured URLs (rate apps, webhooks) reach only public addresses and are signed with the app's secret (`outbound.rs`); `outbound.allow_private` (`HYPHA_ALLOW_PRIVATE_CALLBACKS=true`) allows localhost apps in development. Postgres uses TLS when the URL's `sslmode` asks for it (`prefer` by default, `require` for managed databases), verified against the OS trust store.
- Configuration (design note 0017): operator settings (bind address, proxies, body limit, pool, media, auth lifetimes, job switches and timers, the dispatcher's batch, lease, retries and retention, rate limits) live in `hypha.config.toml` (`HYPHA_CONFIG` names another file; without one, every default), typed for editors by `hypha.config.schema.json` (start the file with `#:schema ./hypha.config.schema.json`). Secrets and first-start values stay environment-only (`DATABASE_URL`, `HYPHA_SECRET_KEY`, `HYPHA_S3_ACCESS_KEY_ID`/`_SECRET_ACCESS_KEY`, `HYPHA_OWNER_*`, `HYPHA_STORE_NAME`); the variables that predate the file (`HYPHA_BIND`/`PORT`, `HYPHA_TRUSTED_PROXIES`, `HYPHA_ADMIN_URL`, `HYPHA_ALLOW_PRIVATE_CALLBACKS`, `HYPHA_MEDIA_*`, `HYPHA_S3_ENDPOINT`/`_REGION`/`_BUCKET`/`_CREATE_BUCKET`) still work and win over it. `cargo run -p hypha-host-axum -- config` prints the settings in effect; after changing `hypha-config`'s file types, `cargo run -p hypha-host-axum -- config schema` rewrites the schema (committed; a test fails while it's stale). Key names are a contract with operators: never rename one.
- OpenAPI (design note 0010): after changing routes or DTOs, `cargo run -p hypha-host-axum -- openapi` rewrites `openapi/admin.json` and `openapi/storefront.json` (committed; a test fails while they're stale). The running host also serves them at `/admin/openapi.json` and `/storefront/openapi.json`.
- End-to-end check against a freshly started host on a fresh database (Git Bash on Windows; the script reuses handles and countries): `docker compose exec -T postgres psql -U hypha -c "DROP DATABASE IF EXISTS hypha_e2e" -c "CREATE DATABASE hypha_e2e"`, then start the host through cargo (`cargo run -p hypha-host-axum`, so `.cargo/config.toml`'s `HYPHA_S3_*` point it at the compose S3 server) with `DATABASE_URL=postgres://hypha:hypha@localhost:5432/hypha_e2e`, a `HYPHA_SECRET_KEY` `HYPHA_OWNER_EMAIL=owner@example.com HYPHA_OWNER_PASSWORD=e2e-owner-password` (the script logs in as that owner) and `HYPHA_ALLOW_PRIVATE_CALLBACKS=true` (its webhook receiver listens on localhost, with python3), and run `bash scripts/e2e.sh` (`HYPHA_URL` for another port). Asserts status + error `code` per step, exits non-zero on failure. Run it after changing routes, DTOs or error mapping, and add a step for new routes.
- Postgres (Docker Desktop): `docker compose up -d`; `cargo test -p hypha-store-postgres` runs the repository contract against it and `cargo test -p hypha-host-axum` the route tests (each test gets its own schema).

## Architecture (hexagonal / ports and adapters)

Dependencies point inward: hosts → domain crates → core. Core and domain crates never depend on storage, HTTP or runtimes.

Domain crates are layered; a crate may only depend on layers below it (Cargo rejects cycles, so a wrong edge forces a painful restructure later):

| Layer | Crates | May depend on |
| --- | --- | --- |
| Hosts | `hypha-host-axum` | anything |
| Storage adapters | `hypha-store-postgres` (tokio-postgres; native and Workers via Hyperdrive), `hypha-store-s3` (files over the S3 API: R2, S3; HTTP through its `HttpClient` port) | domain crates, core; never hosts |
| Configuration | `hypha-config` (design note 0017: `hypha.config.toml` into each crate's settings; parses a string, so it builds for wasm) | workflows, domain crates, core; only hosts depend on it |
| Workflows | `hypha-checkout` (cart → order), `hypha-order-actions` (fulfil, cancel a fulfilment, cancel an order: orders, fulfilments and stock in one batch; design note 0018), `hypha-dispatch` (delivering domain events: fan-out, retries, webhooks to apps through the host's `WebhookSender` port, and the in-process handlers the host passes it; design note 0016) | composing and leaf domains, core |
| Composing domains | `hypha-cart`, `hypha-users`, `hypha-merchandising` | leaf domains, core (`hypha-users` → `hypha-auth` only; `hypha-merchandising` → `hypha-products`, `hypha-media` only) |
| Leaf domains | `hypha-products`, `hypha-markets`, `hypha-pricing`, `hypha-tax`, `hypha-inventory`, `hypha-customers`, `hypha-stores`, `hypha-orders`, `hypha-fulfillment`, `hypha-auth`, `hypha-media`, `hypha-shipping`, `hypha-apps` | core; `hypha-pricing` → `hypha-markets` only |
| Core | `hypha-core` | nothing internal |

Leaf functions take the plain values they need (IDs, `Price`), not another leaf's aggregate. E.g. `resolve_price` takes `ProductId`, `VariantId` and the base `Price` rather than `&Product`; the composing command (cart) loads the product and passes them in. Ask before adding a new edge between domain crates.

- `hypha-core`: shared types only — `Money`/`Price`/`BasisPoints` (`money/`), prefixed IDs (`ids.rs`), `CountryCode`, `Email`, `Address`, `Scope`, `Ctx`/`Actor`, generic ports (`IdGenerator`, `Clock`, `HasBatch`, `RepoError` in `ports.rs`), `Timestamp` (`time.rs`, µs since the epoch), list pages (`page.rs`: `PageRequest`/`Page`, newest first by UUIDv7 ID; hosts expose an opaque `cursor`, design note 0012; a repo's `list` returns the domain's summary read model, e.g. `ProductSummary` from `Product::summary`, which adapters may compute in storage), idempotency keys (`idempotency.rs`: a keyed command checks `earlier_result` first, then stages an `IdempotencyRecord` in the same batch as its write, and after *any* failed keyed write looks the key up again and replays the winner, since a racing request with the same key can fail it on the cart or order before the key; see `hypha-cart`'s `write_cart` and `hypha-checkout`'s retry loop). No domain logic, no I/O.
- Domain crates (`hypha-products`, `hypha-markets`, `hypha-pricing`, `hypha-tax`, `hypha-inventory`, `hypha-customers`, `hypha-orders`, `hypha-cart`, and the `hypha-checkout` workflow): aggregates with private fields and validated constructors, a repository trait (port) per aggregate in `repo.rs`, error enums in `error.rs` (a crate's `CommandError` sits in `commands.rs`), and commands in `commands.rs` (`hypha-products` is the simplest template; `hypha-cart` shows a command that composes several domains; `hypha-checkout` writes several aggregates in one batch and retries when it loses a race).
- `hypha-merchandising` (design note 0014): how products are presented. Attaching media writes the product and its asset usages (`hypha-media`'s `StageAssetUsages`) in one batch; the usage → asset reference is a storage rule (`RepoError::Reference`), so an asset in use can't be deleted. Product responses are built from its `ProductView` (the product plus its media's assets).
- `hypha-fulfillment` and `hypha-order-actions` (design note 0018): a `Fulfillment` (`ful_…`) is what left one location for an order, with tracking; the order counts each line's `fulfilled_quantity` and derives `fulfillment_status`. `hypha-order-actions` is the workflow that writes the fulfilment, the order and the inventory items in one batch (`fulfill`, `cancel_fulfillment`, `cancel_order`, retried on a lost race like checkout) and derives what's left to ship by location (`order_view`). Buyer emails (`BuyerEmail`) are sent by the host after the commit. Every store has a location: the host creates "Default" on first start.
- Event handlers (design note 0019, section 5.1): an in-process destination is a `hypha_core::EventHandler<P>` (a stable `name`, the event types it `wants`, an idempotent `handle`), bounding `P` on only the repositories it uses, and living in the crate whose work it does (`VariantCleanup` in `hypha-dispatch`, search's in `hypha-search`). The host lists the set in `hypha-host-axum/src/handlers.rs` (a tuple: static dispatch, so `Send` stays provable) and the dispatcher runs whatever it's given; never add a handler by editing the dispatcher.
- `hypha-apps` (design note 0016, section 8): external apps (`app_<name>`), each with a sealed signing secret, an optional webhook and event subscriptions (`App::wants`). Shipping's rate settings (`AppProvider`) live in `hypha-shipping` under the same key; storage links them (a provider needs its app, `shipping_provider_app`, and goes with it), and the host joins them when calling (`HostRates`). Its commands also list an app's deliveries, retry one and read an event (`OutboxRepo`); webhooks are sent by `hypha-dispatch` through the host's `WebhookSender` (`webhooks.rs`: the envelope, `Hypha-Event-Id`/`-Type`/`-Delivery-Id`).
- Settings (design note 0017): a crate with tunable values owns a plain settings struct whose `Default` holds them (`AuthSettings`, read through `AuthEnv`'s `HasAuthSettings`; `DispatchSettings` with its `RetrySchedule`; `MediaSettings`), passed in like a port (no globals); aggregates take the one value they need (`Session::active(…, lifetime)`). `hypha-config` builds them from `hypha.config.toml`, its file types (`file.rs`) take their defaults from those `Default`s, and its checks (`check` in `lib.rs`) list every broken rule with its key. A new setting is a field on the crate's struct, a key in `file.rs` (with a doc comment: it's the schema's description), a check if it has limits, and the regenerated schema. Contracts with clients (event types, TOTP's digits, page limits, per-product limits) stay constants.
- `hypha-auth` and `hypha-users` (design note 0008): who is calling. `hypha-auth` holds identities with typed credentials (password, TOTP, recovery codes; stored as kind + lookup + JSON so a new login method needs no column), server-side sessions (a pending state while a second factor is owed), API keys, password resets and prefixed tokens stored only as SHA-256; hashing and sealing are ports (`PasswordHasher`, `SecretBox`), and its commands take one `env: &impl AuthEnv` bundling the non-storage ports. `hypha-users` holds roles (named scope sets; the owner role has every scope), users and invites, and the staff flows (`login`, `accept_invite`, `authenticate_staff`). Nobody grants a scope they lack (`require_grantable`); a write scope implies its read scope (`Scope::implied_by`, applied in `Ctx::has_scope`).
- `hypha-testkit`: in-memory repos for every port (`InMemoryProductRepo`, `InMemoryCartRepo`, …) and deterministic ports (`SequentialIds`, `FixedClock`), for the domain crates' fast command tests (hosts run on Postgres only and don't depend on it). It depends on domain crates, so domain crates use it only as a dev-dependency from their `tests/` folder.
- `hypha-host-axum`: the only place with Tokio, HTTP, auth parsing, logging subscribers (`tracing`) and real ID generation (`UuidV7Ids`). `routes/` holds one module per area with its own request/response DTOs (never serialize domain types directly); `error.rs` maps every crate's `CommandError` to a status (403 scope, 404 resource in the URL, 409 conflict or the state of the resource in the URL, 422 invalid input incl. unknown IDs in the body (except the routes listed at the top of `error.rs` that store other domains' IDs unchecked), 500 storage with the message hidden) and fills `details` for errors that carry data a client acts on (shortages, unavailable lines, totals); `extract.rs` wraps `Json`/`Path` so even axum's rejections return `{"code": …, "error": …, "details": …}`; routes whose command takes an idempotency key use `KeyedJson` (reads the `Idempotency-Key` header, fingerprints the request) and `idempotent_response`. Request DTOs are `#[serde(deny_unknown_fields)]`; PATCH bodies follow JSON Merge Patch (absent keeps, `null` clears) via the `patch::nullable` / `patch::non_null` field helpers. List routes (design note 0012) share `routes/page.rs`: they take `ListQuery<Filters>` (the page's `cursor`/`limit` read apart from the route's own `deny_unknown_fields` filters), list `PageParams` and the filters in `params(...)` (the documents add the paging errors to routes with exactly those parameters), and return a `PageResponse<ItemDto>` named by a type alias (`type ProductPage = PageResponse<ProductResponse>;`). Storage is `PgStorage` (`state.rs`; deadpool pool, one `PgStore` per request) behind the `Storage` trait, the seam a Workers storage would plug into; handlers are generic over it and get the request's ports from `caller.authenticate(&state)` (see below). Routes are listed once, in the `route_table!` macro in `routes/mod.rs` (`[surface, METHOD, "/path", module::handler]`): it builds the router per concrete storage (axum can only prove handler futures `Send` for concrete types) and the OpenAPI documents (`routes/openapi.rs`). There are two API surfaces (design note 0010): `/admin/*` (staff sessions and secret keys) and `/storefront/*` (publishable keys), each with its own DTOs where they differ (a storefront never sees drafts or admin fields). A new route is a table row plus a handler with `#[utoipa::path(...)]` (method and path as in the table, `params`, `request_body`, the success response, and `extensions(("x-hypha-scopes" = json!([...])))`) and `utoipa::ToSchema` on its DTOs; operation IDs, tags, security and the standard error responses are added from the table. Without the annotation the table doesn't compile. Every handler takes a `Caller` (`Caller<Admin>`, the default, or `Caller<Storefront>`; the wrong kind of credential for the surface is a 403 before any lookup) (`extract.rs`), the one place a request becomes a `Ctx`: the extractor only reads `Authorization: Bearer` (a staff session `hypha_sess_…`, the role's scopes read fresh each request, or an API key `hypha_sk_…` / `hypha_pk_…`) or `X-Publishable-Key` (none is 401 `unauthenticated`), and the handler's first line is `let (ports, ctx) = caller.authenticate(&state).await?;` (a bad token is 401 `invalid_token`): one pooled connection per request, and the only way to ports besides `state.public_ports()`, which is for routes that need no credentials. Parse bodies only after that: `JsonBody` and `KeyedJson` buffer the bytes, and `body.parse()?` / `req.parse()?` come after `authenticate`, so strangers get a 401 before any JSON work. `/me` routes take `StaffCaller` the same way (API keys get 401 `session_required`). The public routes (login, MFA, password reset, invite acceptance) take a `ClientIp` (`client_ip.rs`) and call `rate_limit::enforce(&state.limiter, Rule::…, key)` per address before parsing and per email after (`429 rate_limited` with `Retry-After`); every limit is a `Rule` with its quota in `rate_limit.rs`, behind the `RateLimiter` port (in memory for now). Work that must outlive the response runs in `state.background` (a few slots; drained on shutdown), spawned per concrete storage (`Storage::spawn_password_reset`) for the same `Send` reason as `router!`. Timed work (delivering events, pruning, the media sweep) runs in `jobs.rs`'s runner, started once through `Storage::start_jobs` and stopped on shutdown; each job is a step from a domain crate (`hypha_dispatch::fan_out`, …) that says whether there's more, so a Workers host can call the same steps from a Cron trigger. `HostEnv` (`state.rs`) provides OS randomness, Argon2id on blocking threads, the `SecretBox` under `HYPHA_SECRET_KEY`, and a logging `Notifier`.

Command shape (see `crates/hypha-products/src/commands.rs`): `async fn cmd(ctx: &Ctx, repo: &impl Repo, ids: &impl IdGenerator, input: RawInput) -> Result<_, CommandError>`; first line `ctx.require(Scope::...)?`, then validate raw input through domain constructors. `CommandError` composes lower errors via `#[from]`.

When a command needs more than one repository, take `ports: &S` bound on the accessor traits it uses: each crate defines `HasXxx` (associated repo type + `fn xxx(&self)`) next to its repo traits in `repo.rs`, e.g. `create_cart<S: HasMarkets + HasCarts>`. A composing crate names its union with a blanket impl (`CartPorts`, `PricingPorts` in `crates/hypha-cart/src/commands.rs`), so implementors never list them. Hosts and tests implement the accessors once (`hypha_testkit::InMemoryPorts`, `PgStore`); a new repository adds one `HasXxx`. Static dispatch keeps `Send` provable; don't bundle them into `&dyn` objects.

## Hard constraints

- Core and domain crates must compile for `wasm32-unknown-unknown`: no Tokio, threads, `std::fs`, `SystemTime::now()` or random UUID generation there. Time, IDs and randomness come in through ports.
- Repository traits use `async fn` with `#[allow(async_fn_in_trait)]` and **no `Send` bound**, on purpose (Cloudflare futures are `!Send`). Hosts use concrete types/generics so the compiler can prove `Send`; never `&dyn` for ports used across `.await`.
- Authorization lives in commands (`ctx.require(Scope::...)?`); authentication lives in hosts. Commands never trust raw input.

## Code standards

- Money: integer minor units (`i64`), never floats, capped at ±`Money::MAX_AMOUNT` (2⁵³ − 1) so JSON clients represent every amount exactly; `Money::new` is fallible. Checked arithmetic returning `Result`; percentages as `BasisPoints` with round-half-away-from-zero; `i128` for intermediates.
- Newtypes with validated constructors for anything with rules (`Handle`, `Price`, `CountryCode`, IDs). Don't derive `Deserialize` on validated types unless via `#[serde(try_from = ...)]`.
- IDs: `define_id!` macro in `hypha-core/src/ids.rs` — UUID inside, prefixed string at the edges (`prod_…`, `var_…`, `mkt_…`, `pl_…`). Store native UUIDs; UUIDv7 in hosts.
- Errors: `thiserror` enums with specific variants (no stringly errors). Every error enum implements `hypha_core::ErrorCode` with an exhaustive `match` (no `_` arm): stable snake_case codes, never renamed once released, wrappers delegate to the inner error. Messages use `Display` for domain values (`EUR`, `active`); raw input the caller sent (a string or char that failed to parse) is quoted with `{0:?}`, so blanks and control characters stay visible. No `unwrap`/`expect`/panics in non-test code except documented invariants.
- Aggregates own their children (Product owns Variants); cross-aggregate rules live in commands/functions above them.
- Migrations are per module: `hypha_store_postgres::CORE` is core's `MigrationSet`; a spore ships its own set (module `"spore_<name>"`, tables prefixed the same way), passed to `migrate(&mut client, &[CORE, …])`. Append only: an applied migration is never edited, renamed or reordered (the runner checks names and fails).
- Persistence (design note `docs/design/0001-postgres-storage.md`): aggregate roots implement `Versioned`; repos have `insert(&mut T)` / `update(&mut T)`, never an upsert. `update` from an old version fails with `RepoError::StaleVersion`. Uniqueness rules are repo `keys::*` constants reported as `RepoError::Duplicate(key)`; commands keep a read-then-check for precise errors **and** map the `Duplicate` from the write to the same domain error (a race must look like a normal duplicate). In-memory repos are built on `hypha-testkit`'s `Table`, which enforces versions and keys like a database. A command writes one aggregate through its repo, or several through one `HasBatch` commit (`hypha-core/src/ports.rs`): each crate has a `StageXxx` trait next to its repo trait (`StageCarts`), implemented by the adapters' batch types (`InMemoryBatch`, `PgBatch`), and staging moves the aggregate to the version it gets on commit. `reserve_stock` / `release_stock` (no batch of their own) still write every item at once through `InventoryItemRepo::update_many`, all or nothing (0004, I7). Domain events (design note 0016): an aggregate records them (`hypha_core::Recorded`; a `Recorder`, or a coalescing type like products' `Changes`), and every write of it (repo `insert`/`update`, `Stage*` in a batch) takes them and writes them to `outbox_events` in the same transaction, stamped with the ports' actor (`ActingAs`, set in `Caller::authenticate`); set-based writes (catalog membership, fixed prices, tax-class assignment) are staged in a batch with their events (`StageCatalogProducts`, `StageEvents`, …); the repos' own set-based methods record nothing and are for setting up data. Take an aggregate's events before copying it into a batch, so the stored copy carries none. Aggregate roots also carry `Stamps` (`created_at`/`updated_at`, `hypha_core::Stamped`): adapters set them with `stamp_insert`/`stamp_update` from the ports' clock (`PgStore::new(conn, clock)`; in memory, the shared `InMemoryOutbox`'s fixed clock) before taking the snapshot, in repo writes and when staging. Payloads are contract types in the domain crate's `events.rs` (subject and what changed, not the aggregate; a reshaped field is a new version). `restore` re-runs constructor rules, so tightening a rule (a shorter max length, a newly required field) needs a migration that fixes or rejects existing rows first, or those rows stop loading (500).
- Getters return values for `Copy` types and references (`&str`, slices) for owned heap data.
- Workspace lints: `unsafe_code = "forbid"`, `clippy::all = "warn"`. Code must be fmt-clean and clippy-warning-free.

## Testing

- Unit tests in `#[cfg(test)] mod tests` at the bottom of each file; one rule per test; test boundaries (0 vs -1, exact rounding halves); compare expected errors exactly with `assert_eq!(result, Err(...))`, never via `unwrap`.
- Command tests are integration tests in each crate's `tests/` folder using `hypha-testkit` (avoids duplicate-crate issues with dev-dependencies).
- Async in tests via `pollster::block_on`; deterministic IDs via `SequentialIds` and `Uuid::from_u128(n)`; time via `FixedClock` (commands take `clock: &impl Clock` like `ids`).
- Repository contract: `hypha_testkit::contract::{product_repo, market_repo, catalog_repo, price_list_repo, cart_repo, tax_class_repo, tax_region_repo, location_repo, inventory_item_repo, customer_repo, order_repo, fulfillment_repo, idempotency_repo, batch, identity_repo, session_repo, api_key_repo, password_reset_repo, user_repo, role_repo, invite_repo, staff_batch, asset_repo, asset_usages, shipping_zone_repo, app_provider_repo, app_repo, outbox}` and `blob_store` (file storage: run with the client's upload and download as closures; the S3 adapter runs it against MinIO) define what every repo adapter must do (round trips, versions, unique keys, batched methods). The suite is behind testkit's `contract` feature (so hosts don't ship it): adapters enable it as a dev-dependency, and the in-memory run (`crates/hypha-testkit/tests/contract.rs`) needs `--features contract` when testing that crate alone (`cargo test --workspace` enables it). Every new adapter must run it. Batch methods state caller preconditions (parent exists, no duplicates) in their docs, and the contract checks that breaking them fails. When a repo trait gains a method or a unique key, add a contract scenario first.
