# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Hypha (working name): open-source, modular e-commerce API in Rust (edition 2024, Cargo workspace, `crates/*`).
- **Modular**: one crate per domain; behavior is extended through plugins ("spores") via traits and events, not by editing core.
- **Agent-friendly, in two specific ways** (shopping agents are *not* the target of the core API):
  1. **Building Hypha**: the codebase is meant to be easy for coding agents to extend: core, domain crates and plugins ("spores"). Favor explicit types, small crates with clear ports, exact errors and fast deterministic tests over cleverness.
  2. **Admin assistance**: agents will help merchants operate the system from the admin panel. Every operation is a command with typed input, required scopes and typed errors, so the same surface can be exposed over HTTP, MCP and CLI; such agents act as `Actor::Agent` with their own scopes.
  - Agentic *shopping* goes through a separate adapter for the Universal Commerce Protocol (UCP, ucp.dev; planned via ucphub.ai), not through the core commands directly. Design storefront-facing read models (e.g. priced carts) so they map cleanly onto UCP, e.g. per-line problems → UCP `messages` with a `path` to the line.
- **Large catalogs**: sparse explicit variants (never generate the Cartesian product of options); Shopify-style markets / catalogs / price lists.
- **Multi-host**: the same core runs on Cloudflare Workers (WASM), AWS Lambda, Vercel and a plain VPS (axum).
- It's also a Rust learning project for the maintainer (Danilo, TypeScript background). See "Working with Danilo".

## Commands

Run all four before considering work done (and, for TypeScript changes, `pnpm fmt`, `pnpm lint`, `pnpm lint:react` and `pnpm typecheck`); CI (`.github/workflows/ci.yml`) runs them too, plus e2e and the TypeScript checks, with clippy warnings as errors (the tests need Postgres: `docker compose up -d`; `.cargo/config.toml` points `DATABASE_URL` at it, and an exported `DATABASE_URL` wins):

```bash
cargo fmt --all
cargo clippy --workspace --all-targets
cargo test --workspace
cargo build -p hypha-core -p hypha-products -p hypha-markets -p hypha-pricing -p hypha-cart -p hypha-tax -p hypha-inventory -p hypha-customers -p hypha-stores -p hypha-orders -p hypha-fulfillment -p hypha-payments -p hypha-notifications -p hypha-mail -p hypha-checkout -p hypha-order-actions -p hypha-dispatch -p hypha-auth -p hypha-users -p hypha-media -p hypha-merchandising -p hypha-shipping -p hypha-apps -p hypha-extensions -p hypha-oauth -p hypha-channels -p hypha-categories -p hypha-search-index -p hypha-search -p hypha-config -p hypha-store-postgres -p hypha-store-s3 -p hypha-mail-resend -p hypha-http -p hypha-host-workers --target wasm32-unknown-unknown
```

Extend the wasm build list when a domain crate or storage adapter is added. `hypha-http` is on it: anything a runtime provides goes through `host.rs`, never a Tokio or OS call (design note 0026).

- Single crate's tests: `cargo test -p hypha-products`
- Single test by name: `cargo test -p hypha-products rejects_same_handle_products`
- Only an integration test file: `cargo test -p hypha-products --test commands`
- Run the HTTP host (binds `server.bind`, `127.0.0.1:3000` by default; `RUST_LOG` respected; Ctrl+C or SIGTERM drains in-flight requests; `GET /health` for probes; `-- setup` does a start's preparation (migrations, store, owner, location, search index) and exits without serving): `HYPHA_SECRET_KEY=… cargo run -p hypha-host-axum`, on Postgres only (`DATABASE_URL`, the compose database by default under cargo; migrations run on startup). `HYPHA_SECRET_KEY` is 64 hex characters from `openssl rand -hex 32`, kept across restarts since it seals 2FA secrets. Every route but `/health` and the login ones needs credentials (design note 0008): on first start, `HYPHA_OWNER_EMAIL` and `HYPHA_OWNER_PASSWORD` create the owner, who logs in with `POST /auth/login`. Emails (invites, resets) are logged, not sent; `server.admin_url` turns their tokens into links. The public routes are rate limited per client address (design note 0009): behind a proxy or load balancer, set `server.trusted_proxies` (CIDR ranges) so `X-Forwarded-For` is believed from those peers, or every client shares one limit (a server-rendered storefront is such a proxy: it passes shoppers' addresses). Calls to merchant-configured URLs (rate apps, webhooks) reach only public addresses and are signed with the app's secret (`outbound.rs`); `outbound.allow_private` (`HYPHA_ALLOW_PRIVATE_CALLBACKS=true`) allows localhost apps in development. Postgres uses TLS when the URL's `sslmode` asks for it (`prefer` by default, `require` for managed databases), verified against the OS trust store.
- Configuration (design note 0017): operator settings (bind address, proxies, body limit, pool, media, auth lifetimes, job switches and timers, the dispatcher's batch, lease, retries and retention, rate limits) live in `hypha.config.toml` (`HYPHA_CONFIG` names another file; without one, every default), typed for editors by `hypha.config.schema.json` (start the file with `#:schema ./hypha.config.schema.json`). Secrets and first-start values stay environment-only (`DATABASE_URL`, `HYPHA_SECRET_KEY`, `HYPHA_S3_ACCESS_KEY_ID`/`_SECRET_ACCESS_KEY`, `HYPHA_SMTP_PASSWORD`, `HYPHA_RESEND_API_KEY`, `HYPHA_OWNER_*`, `HYPHA_STORE_NAME`); the variables that predate the file (`HYPHA_BIND`/`PORT`, `HYPHA_TRUSTED_PROXIES`, `HYPHA_ADMIN_URL`, `HYPHA_ALLOW_PRIVATE_CALLBACKS`, `HYPHA_MEDIA_*`, `HYPHA_S3_ENDPOINT`/`_REGION`/`_BUCKET`/`_CREATE_BUCKET`) still work and win over it, as do `[email]`'s (design note 0028: `HYPHA_EMAIL_SENDER`, `HYPHA_EMAIL_FROM`, `HYPHA_SMTP_HOST`/`_PORT`/`_TLS`, which `.cargo/config.toml` points at the compose Mailpit with: every email of a `cargo run` lands in http://localhost:8025). `cargo run -p hypha-host-axum -- config` prints the settings in effect (`config rate-limits`: the Worker's Rate Limiting bindings as JSON, named, slotted and sized by `Rule`); after changing `hypha-config`'s file types, `cargo run -p hypha-host-axum -- config schema` rewrites the schema (committed; a test fails while it's stale). Key names are a contract with operators: never rename one.
- OpenAPI (design note 0010): after changing routes or DTOs, `cargo run -p hypha-host-axum -- openapi` rewrites `openapi/admin.json`, `openapi/storefront.json` and `openapi/extensions.json` (design note 0029: every extension point as an OpenAPI 3.1 `webhooks` entry keyed by its name, with `x-hypha-extension: {point, version}`, the request body and the 200 answer) (committed; a test fails while they're stale). The running host also serves them at `/admin/openapi.json` and `/storefront/openapi.json`.
- End-to-end check against a freshly started host on a fresh database (Git Bash on Windows; the script reuses handles and countries): `docker compose exec -T postgres psql -U hypha -c "DROP DATABASE IF EXISTS hypha_e2e" -c "CREATE DATABASE hypha_e2e"`, then start the host through cargo (`cargo run -p hypha-host-axum`, so `.cargo/config.toml`'s `HYPHA_S3_*` point it at the compose S3 server) with `DATABASE_URL=postgres://hypha:hypha@localhost:5432/hypha_e2e`, a `HYPHA_SECRET_KEY` `HYPHA_OWNER_EMAIL=owner@example.com HYPHA_OWNER_PASSWORD=e2e-owner-password` (the script logs in as that owner) and `HYPHA_ALLOW_PRIVATE_CALLBACKS=true` (its webhook receiver listens on localhost, with python3, and serves the OAuth steps' app manifest) and `HYPHA_ADMIN_URL=http://admin.e2e.test` (the consent page `/oauth/authorize` sends to; the script plays the admin), and run `bash scripts/e2e.sh` (`HYPHA_URL` for another port). Asserts status + error `code` per step, exits non-zero on failure. When the host sends over SMTP (a `cargo run` does, to the compose Mailpit) and Mailpit's API answers at `MAILPIT_URL` (default http://localhost:8025), it also checks the order and invite emails arrived there and deletes them; with another sender (the log, as on Workers) or `E2E_MAILPIT=0` it skips those. Run it after changing routes, DTOs or error mapping, and add a step for new routes.
- The API on Workers (design note 0026, `crates/hypha-host-workers`): the same routes over Hyperdrive, with an isolate's state (config, secret key, store, key cache, limiter counts, routes) kept between requests and an `AppState` per request (its `waitUntil`). It runs no migrations and creates no store: set the database up first with the native host's `setup` (W9: migrations, the store, the owner, the default location, the search index, then it exits: `DATABASE_URL=…/hypha_workers HYPHA_SECRET_KEY=… HYPHA_OWNER_EMAIL=… HYPHA_OWNER_PASSWORD=… cargo run -p hypha-host-axum -- setup`; a reset database needs a restarted Worker, since the isolate keeps the store's ID). Copy `.dev.vars.example` to `.dev.vars` with the same key, then `wrangler dev --port 3989` in that folder (`localConnectionString` points at the compose `hypha_workers` database) and `HYPHA_URL=http://localhost:3989 bash scripts/e2e.sh`. One cron a minute runs dispatch and search sync when the `JOBS` KV namespace's marks say there's work (W7, `marks.rs`: `written` when a run left work, `checked` when a tick's run left none, `due` from `OutboxRepo::next_due`; an hourly tick runs them regardless), so a quiet store's ticks don't touch Postgres, and the other jobs on the ticks that start their `jobs.<job>.interval` (`curl "http://localhost:3989/cdn-cgi/handler/scheduled?cron=*+*+*+*+*"` triggers one locally); a write that committed events (or retried a delivery) runs dispatch and search sync in `waitUntil`, starting no delivery that couldn't finish within its 30 seconds (`jobs::dispatch_by`). One `AppState` and router per isolate; an event's `waitUntil` and write flag reach them through `Scoped` (the event is current while its future is polled). Its Hyperdrive must be created with `--caching-disabled`: the API's reads outside transactions (sessions, keys) must not be served from a cache. From our own Workers (through a Service Binding, sending the deployment's `HYPHA_CALLER_KEY` as `X-Hypha-Caller`; not the binding's props, which Cloudflare drops for a Worker with a placement), the client's address is the caller's `X-Forwarded-For`, otherwise `CF-Connecting-IP` (`peer.rs`). Its `ids` (UUIDv7 in order within a millisecond), `limiter` (W8: each check counts in the isolate, GCRA with the quota's exact shape, then on the rule's Rate Limiting binding (`Rule::binding`, `binding_slot`, `binding_limit` in `hypha-http`), which caps all isolates together at the most the quota allows in a minute; `wrangler.toml`'s bindings are the defaults', a test keeps them in step), `marks` and `schedule` are portable and tested natively.
- Postgres (Docker Desktop): `docker compose up -d`; `cargo test -p hypha-store-postgres` runs the repository contract against it and `cargo test -p hypha-host-axum` the route tests (each test gets its own schema; `cargo test -p hypha-http` the HTTP layer's own).

## Architecture (hexagonal / ports and adapters)

Dependencies point inward: hosts → domain crates → core. Core and domain crates never depend on storage, HTTP or runtimes.

Domain crates are layered; a crate may only depend on layers below it (Cargo rejects cycles, so a wrong edge forces a painful restructure later):

| Layer | Crates | May depend on |
| --- | --- | --- |
| Hosts | `hypha-host-axum` (the binary: startup, config, migrations, serving) on `hypha-http` (the routes, extractors, errors, DTOs, OpenAPI and host state; design note 0026, W3) | anything |
| Storage adapters | `hypha-store-postgres` (tokio-postgres; native and Workers via Hyperdrive), `hypha-store-s3` (files over the S3 API: R2, S3; HTTP through its `HttpClient` port) | domain crates, core; never hosts |
| Configuration | `hypha-config` (design note 0017: `hypha.config.toml` into each crate's settings; parses a string, so it builds for wasm) | workflows, domain crates, core; only hosts depend on it |
| Workflows | `hypha-checkout` (cart → order and its payment, choosing a payment method; design note 0027), `hypha-order-actions` (fulfil, cancel a fulfilment, cancel an order, record money received: orders, fulfilments, payments and stock in one batch; design notes 0018, 0027), `hypha-dispatch` (delivering domain events: fan-out, retries, webhooks to apps through the host's `WebhookSender` port, and the in-process handlers the host passes it; design note 0016), `hypha-search` (building search documents per market, the `SearchIndexer` handler, the sync job, searching a shopper's market; design note 0019), `hypha-mail` (emails: each template's context from orders, fulfilments, payments, the store and media, the `Mailer` handler, previews, test sends, resends, the staff flows' emails; design note 0028) | composing and leaf domains, core |
| Composing domains | `hypha-cart`, `hypha-users`, `hypha-merchandising`, `hypha-oauth` | leaf domains, core (`hypha-users` → `hypha-auth` only; `hypha-merchandising` → `hypha-products`, `hypha-media`, `hypha-categories` only: a category's image, design note 0022 Q5; `hypha-oauth` → `hypha-apps`, `hypha-auth` only) |
| Leaf domains | `hypha-products`, `hypha-markets`, `hypha-pricing`, `hypha-tax`, `hypha-inventory`, `hypha-customers`, `hypha-stores`, `hypha-orders`, `hypha-fulfillment`, `hypha-payments`, `hypha-auth`, `hypha-media`, `hypha-shipping`, `hypha-apps`, `hypha-search-index`, `hypha-channels`, `hypha-categories`, `hypha-notifications`, `hypha-extensions` | core; `hypha-pricing` → `hypha-markets` only |
| Core | `hypha-core` | nothing internal |

Leaf functions take the plain values they need (IDs, `Price`), not another leaf's aggregate. E.g. `resolve_price` takes `ProductId`, `VariantId` and the base `Price` rather than `&Product`; the composing command (cart) loads the product and passes them in. Ask before adding a new edge between domain crates.

- `hypha-core`: shared types only — `Money`/`Price`/`BasisPoints` (`money/`), prefixed IDs (`ids.rs`), `CountryCode`, `Email`, `Address`, `Scope`, `Ctx`/`Actor`, generic ports (`IdGenerator`, `Clock`, `HasBatch`, `RepoError` in `ports.rs`), `Timestamp` (`time.rs`, µs since the epoch), list pages (`page.rs`: `PageRequest`/`Page`, newest first by UUIDv7 ID; hosts expose an opaque `cursor`, design note 0012; a sorted list (design note 0024) takes `PageRequest<Keyset<Id>>`, the last item's `SortKey` with its ID, its order a domain enum like `ProductSort` that adapters map to `ORDER BY key, id` with an index per key, and its route parses with `ListQuery::parse_sorted` (filters implement `SortedFilters`) and answers with `PageResponse::sorted`; a repo's `list` returns the domain's summary read model, e.g. `ProductSummary` from `Product::summary`, which adapters may compute in storage), idempotency keys (`idempotency.rs`: a keyed command checks `earlier_result` first, then stages an `IdempotencyRecord` in the same batch as its write, and after *any* failed keyed write looks the key up again and replays the winner, since a racing request with the same key can fail it on the cart or order before the key; see `hypha-cart`'s `write_cart` and `hypha-checkout`'s retry loop). No domain logic, no I/O.
- Domain crates (`hypha-products`, `hypha-markets`, `hypha-pricing`, `hypha-tax`, `hypha-inventory`, `hypha-customers`, `hypha-orders`, `hypha-cart`, and the `hypha-checkout` workflow): aggregates with private fields and validated constructors, a repository trait (port) per aggregate in `repo.rs`, error enums in `error.rs` (a crate's `CommandError` sits in `commands.rs`), and commands in `commands.rs` (`hypha-products` is the simplest template; `hypha-cart` shows a command that composes several domains; `hypha-checkout` writes several aggregates in one batch and retries when it loses a race).
- `hypha-merchandising` (design note 0014): how products are presented. Attaching media writes the product and its asset usages (`hypha-media`'s `StageAssetUsages`) in one batch; the usage → asset reference is a storage rule (`RepoError::Reference`), so an asset in use can't be deleted. Product responses are built from its `ProductView` (the product plus its media's assets).
- `hypha-fulfillment` and `hypha-order-actions` (design note 0018): a `Fulfillment` (`ful_…`) is what left one location for an order, with tracking; the order counts each line's `fulfilled_quantity` and derives `fulfillment_status`. `hypha-order-actions` is the workflow that writes the fulfilment, the order and the inventory items in one batch (`fulfill`, `cancel_fulfillment`, `cancel_order`, retried on a lost race like checkout) and derives what's left to ship by location (`order_view`). Buyer emails go out through `hypha-mail`'s `Mailer` on the order and fulfilment events, when their `notify_customer` (the routes' `notify`) says so. Every store has a location: the host creates "Default" on first start.
- `hypha-payments` (design note 0027): payment methods (`pm_…`: a provider key, `manual` built in or an app's key `app_<name>`, design note 0029 §3.1; name, instructions, the markets and channels it's offered in, empty for all; enabled; position) and payments (`pay_…`: one attempt to collect an order's total, its method's name, provider and instructions copied; status `pending`/`authorized`/`paid`/`failed`/`voided`/`partially_refunded`/`refunded` with the moves the domain allows). The order's `financial_status` (core's `FinancialStatus`, so both leaves name it) is derived by `hypha_payments::financial_status` and stored; only a batch that changes a payment changes it, with the order in the same commit (checkout: the pending payment; `hypha_order_actions::mark_paid`: the open payment paid, or a `manual` one created for an order without; `cancel_order`: pending ones voided). Providers are the `PaymentProvider` port (`available`, `check_settings`, `start` → `Started { next_action, reference }`, `act` for capture/void/refund; no `Send` bound), listed by each host in its `payments.rs` next to `handlers.rs` (a tuple: `PaymentProviders`, found by key) and named as `Storage::Payments`; `ManualProvider` answers with the instructions. `hypha-http`'s `HostPayments` (`payments.rs`) answers `app_*` keys through the app's `payments.*` points and hands the rest to the host's tuple; `payments.start` carries `customer_email` only when the app's grant has `customer_data:email`. Apps report results through `POST /admin/payments/{id}/events` (`hypha_order_actions::record_payment_event`); an app's own token (`Actor::App`) may report only on payments whose provider is that app (`payment_not_yours`), staff and keys on any. The cart stores only the chosen method's ID; `hypha_checkout::set_payment_method` / `cart_payment_methods` check it's offered (enabled, the cart's market and channel, a provider this build has), and checkout refuses `payment_method_required` unless the total is zero (then no payment at all).
- `hypha-notifications` and `hypha-mail` (design note 0028): the leaf holds templates (`TemplateKey`; Jinja sources rendered by minijinja with strict undefined, the build's defaults in `defaults/` until a merchant saves one), the store's notification settings (branding, sender name, reply-to, staff recipients, the order URL pattern), the record of every message (`ntf_…`, one per (event, template, recipient)) and the `EmailSender` port (no `Send` bound; the host's `log`/`smtp`/`resend` sender is passed apart from the ports, like the `WebhookSender`). The workflow builds each template's context (`context.rs`: its variables are a contract like event payloads, added to, never renamed; money and times arrive formatted, times in the store's zone through jiff's bundled tz database; each kind has a `sample()`), and never sends from the event handler: the `Mailer` renders each message once per event (the template in effect, falling back to the default with a `note` and a warning when a merchant's breaks on real data; saving checks the full sample and two sparse ones) and records it `queued` (or `skipped` when the template is off), idempotent by (event, template, recipient). The `send_notifications` job (`hypha_mail::send_due`, a step in `jobs.rs`; `[jobs.send_notifications]`) leases due messages (`lease_due`, `FOR UPDATE SKIP LOCKED`, expired leases taken over), lets go of the connection, sends only what fits its lease and the host's deadline, then records `sent`, `failed` (a permanent refusal or the end of the retry schedule: never sent again) or `queued` at the next wait. A message is sent twice only if a runner dies between the provider's answer and the record (Resend drops the repeat by the `Idempotency-Key`, the message's ID; SMTP can't). Natively it's its own job in `runner.rs`, woken by `MailQueued`; on Workers it runs in a write's `waitUntil` after dispatch and on the cron when `next_due` says so. Its non-storage inputs are one `MailEnv` the host implements (the sender, the operator's from address, the store, `admin_url`, `order_token`, asset URLs, clock, IDs). `Mailer<E>` (`handler:mailer`) holds the host's `MailEnv`, so a host builds its handler set at startup rather than as a `const`; it answers `order.placed`, and `order.cancelled` / `fulfillment.created` / `fulfillment.updated` when their `notify_customer` (the routes' `notify`) says so. It reads the store through `StoreRepo` on the same ports (model A). Invites, resets and test sends don't queue (an invite's token would be stored): they're sent at once (`send_now`) while the request waits. In the hosts: `hypha-http`'s `mail.rs` has `MailHost` (the `MailEnv`: the `HostMail` sender, `email.from`, the store, `server.admin_url`, `OrderTokens`, the media for the logo's URL), built at startup once the store is known and shared (`Arc`) by `AppState::mail` and the `Mailer` in the handler tuple each host builds with `handlers::handlers(mail)` and keeps in its storage (`Storage::handlers`); the staff flows take `state.staff_env(&ports)` (`StaffEnv`: the `HostEnv`'s auth ports plus a `Notifier<StaffEmail>` through `send_staff`). Routes: `GET`/`PATCH /admin/notification-settings`, `GET /admin/notification-templates`, `GET`/`PUT`/`DELETE /admin/notification-templates/{key}`, `POST …/{key}/preview` and `…/{key}/test` (a staff session's own address; `409 email_not_configured` with the `log` sender), `GET /admin/notifications` (`order`, `template`, `status`), `GET /admin/notifications/{id}`, `POST …/{id}/resend` (201: a new `queued` message); listing and reading messages also need `orders:read` (they hold buyers' addresses); `template_invalid` is 422 with `details: {part, line, message}`, a provider that didn't take a test send is 502 `email_unavailable` / `email_refused`. `staff_new_order`'s context has no `order.url` (the buyer's token stays out of staff mailboxes). HTML output escapes only `& < > " '` (`render::format_value`), so links keep their slashes.
- Event handlers (design note 0019, section 5.1): an in-process destination is a `hypha_core::EventHandler<P>` (a stable `name`, the event types it `wants`, an idempotent `handle`), bounding `P` on only the repositories it uses, and living in the crate whose work it does (`VariantCleanup` in `hypha-dispatch`, search's in `hypha-search`). Each host lists the set in its `handlers.rs` (`hypha-host-axum`, `hypha-host-workers`; a tuple: static dispatch, so `Send` stays provable) and names it as its `Storage::Handlers`, and the dispatcher runs whatever it's given; never add a handler by editing the dispatcher.
- `hypha-search-index` and `hypha-search` (design note 0019): the leaf holds the model and ports (documents, queries, the `SearchIndex` engine, the `SearchQueue`, the settings aggregate, `reference::search`), so storage adapters implement them without depending on the domains documents compose; the workflow builds and syncs. One `SearchDocument` per variant per market (`build_documents`, priced and stocked with the same loaders as carts: `hypha_pricing::load_pricing`, `StockContext::load`), grouped per query (`Group`: listing, product, variant). What a search means is `reference::search`, a plain function: the in-memory engine runs it and the `search_index` contract holds every engine to it, ranking included. The `SearchIndexer` handler only marks targets in the `SearchQueue` (one row per target, so a busy product is rebuilt once); `sync` works them. The engine is passed to commands and jobs apart from the request's ports, like the `WebhookSender`.
- `hypha-channels` (design note 0020): sales channels (`chan_…`, kind `online_store` / `agentic` / `custom`), *where* products are sold, apart from markets (*to whom, at what price*). Publications are set-based channel ↔ product membership (`publish` / `channels_of`, staged with `StagePublications` and their events). A publishable key belongs to one channel and `Ctx::channel()` carries it, so storefront commands never take a channel from input; staff and secret keys have none and see everything.
- `hypha-categories` (design note 0022): product categories (`pcat_…`), a plain tree by parent pointer. Its rules (no cycles, the `max_depth` setting, dense sibling positions) span categories, so commands check them on a `CategoryTree` built from `list_all` and stage the category with its renumbered siblings in one batch. Membership is set-based like publications, with events. Handles and descriptions are core's `Handle` and `Description`, shared with products. `hypha-merchandising` sets a category's image with its asset usage.
- `hypha-apps` (design note 0016, section 8): external apps (`app_<name>`), each with a sealed signing secret, an optional webhook and event subscriptions (`App::wants`). Shipping's rate settings (`AppProvider`) live in `hypha-shipping` under the same key; storage links them (a provider needs its app, `shipping_provider_app`, and goes with it), and the host joins them when calling (`HostRates`). Its commands also list an app's deliveries, retry one and read an event (`OutboxRepo`); webhooks are sent by `hypha-dispatch` through the host's `WebhookSender` (`webhooks.rs`: the envelope, `Hypha-Event-Id`/`-Type`/`-Delivery-Id`). Apps installed through OAuth (design note 0029) also hold their `AppId` (`appid_…`, what `Actor::App` names: `Actor` is `Copy`, the key isn't), the manifest they were installed from (`AppManifest`: `manifest.rs` checks every rule, reports every problem with its path, resolves relative URLs against `app_url`; its JSON Schema `docs/apps/manifest.schema.json` is generated from `ManifestDocument`: `HYPHA_WRITE_MANIFEST_SCHEMA=1 cargo test -p hypha-apps manifest_schema` after changing it), the `Grant` staff approved (`app_grants`) and `uninstalled_at` (an uninstalled app waits for its last webhook, `app.uninstalled`). Fan-out asks `App::wants_event` with the event's subject (`EventRoute`): an app's own `app.*` events go to it alone, and a granted app only gets events about what its grant reads (`event_scope`). Fetching a manifest is the `ManifestFetcher` port (the host's `HostManifests`, an unsigned GET over `HostCalls`). `AppKey` itself lives in core (other leaves name apps), re-exported here.
- `hypha-extensions` (design note 0029, AP3, §15): extension points, the synchronous contracts Hypha calls apps through mid-flow. A point is a type implementing `ExtensionPoint` (`NAME`, `VERSION`, `TIMEOUT`, `ON_FAILURE`, `SCOPE`: what an installed app's grant needs for it to be called (`payments.*` `payments:write`, `search.query` `products:read`, `shipping.rates` `shipping:read`), `Request`/`Response`, an optional `check` on the answer) in `points/` (`ShippingRates`, `PaymentsStart`/`Capture`/`Void`/`Refund`, `SearchQuery`), with a line in `hypha-http`'s `openapi.rs` `points()`; a reshaped body is a new version. `call::<P>(caller, recorder, env, endpoint, request, idempotency_key, correlation)` sends `Hypha-Extension`, `-Version`, `Idempotency-Key` (the host signs and adds `Hypha-Store`), judges the answer (non-2xx or no answer `failed`, `timeout`, a body that isn't `P::Response` or breaks `check` or is over 256 KiB `invalid`; an app's `{code}` kept in the error), records an `ExtensionCall` (`xcall_…`, `extension_calls`, pruned by `jobs.prune.extension_calls_after`) and returns `ExtensionError` (`app_unavailable`, 502, `details: {app, point}`); it never applies the policy: callers do (`apply_policy::<P>` → `Answered::App`/`Fallback`). The host's `ExtensionCaller` is `hypha-http`'s `HostExtensions` (`state.extensions()`) over `HostCalls::exchange_signed`; shipping's `HostRates` calls `shipping.rates` through it, so every rate quote is in `GET /admin/apps/{key}/extension-calls` (the cart as `correlation`; a rate provider's `services` stays a plain signed GET). The leaf can't see apps, so routes load the app first (`list_extension_calls` takes an `AppKey`). Where an app answers a point is `hypha_apps::find_endpoint`, the one rule (read through `hypha-http`'s `HostAppEndpoints`, `app_endpoints.rs`, which also implements core's `AppPoints`): an app installed through OAuth answers where its manifest's `extension_points` say (URLs resolved against `app_url`, the version this build calls), only while it's enabled, not uninstalled and its grant has the point's `SCOPE` (`App::may_answer`); an app made by hand where staff set (`PUT /admin/apps/{key}/extension-points`, table `app_extension_endpoints`; refused `endpoints_from_manifest` for an app with a manifest). Rate apps keep their URL in shipping's `AppProvider` but are gated by `may_answer` too.
- `hypha-oauth` (design note 0029, AP5, §4.1): the OAuth 2.1 flow that installs apps. A client ID is the manifest's URL; `/oauth/authorize` stores an `AuthorizationRequest` (10 minutes) for the admin's consent page (`{server.admin_url}/apps/consent?request=oareq_…`), or answers at once when the app asks for no scope beyond its grant; approving (`apps:write` and every scope asked for) installs the app (a new sealed secret, handed out once with the first tokens) or replaces its grant, and issues a code (`hypha_ac_`, 60 s, once, PKCE S256). Token pairs (`OAuthToken`: access `hypha_at_` 1 h, refresh `hypha_rt_` 30 d, rotating, one family per code exchange) are `hypha-auth` token kinds stored as SHA-256 (`oauth_refresh_tokens`); a rotated refresh token used again revokes every token of the app, a code used twice its family. `authenticate_access_token` gives `Actor::App` the token's scopes as far as the grant still has them, read fresh per request; a missing scope is `app_not_authorized` (`AuthError::AppNotAuthorized`). `uninstall` revokes everything and leaves the app waiting for `app.uninstalled`; a second `DELETE` removes it. Its writes go in one batch with the app's (`StageApps` + `StageOAuth`).
- Personal data (design note 0029, AP10): `hypha-http`'s `redact.rs` is the one place that decides it. Staff sessions see everything; every other admin-surface caller (secret keys, apps) sees names, emails, phones and street addresses only with `customer_data:name|email|phone|address`, else the fields are absent and the object lists them in `redacted` (customers and their address books, orders, carts, email records; searching or sorting by those fields needs the scopes too). Webhook payloads and extension requests are redacted per the receiving app's grant (`Redaction::for_app`; an app without a grant gets no personal data): `payments.start`'s `customer_email` needs `customer_data:email`, and `shipping.rates`' destination keeps only country and company without `customer_data:address` / `:name` / `:phone` (`Redaction::postal_address`), so a rate app quoting by postal code must be installed with `customer_data:address`. The storefront surface isn't redacted (a shopper's own cart and order). A handler returning such a DTO wraps it once: `redact::one(&ctx, Family::Order, dto)` / `redact::page(…)`, returning `Json<Redacted>`; a new DTO family with personal data adds its fields there and a case to the route test `no_admin_route_shows_personal_data_without_its_scopes`.
- Settings (design note 0017): a crate with tunable values owns a plain settings struct whose `Default` holds them (`AuthSettings`, read through `AuthEnv`'s `HasAuthSettings`; `DispatchSettings` with its `RetrySchedule`; `MediaSettings`), passed in like a port (no globals); aggregates take the one value they need (`Session::active(…, lifetime)`). `hypha-config` builds them from `hypha.config.toml`, its file types (`file.rs`) take their defaults from those `Default`s, and its checks (`check` in `lib.rs`) list every broken rule with its key. A new setting is a field on the crate's struct, a key in `file.rs` (with a doc comment: it's the schema's description), a check if it has limits, and the regenerated schema. Contracts with clients (event types, TOTP's digits, page limits, per-product limits) stay constants.
- `hypha-auth` and `hypha-users` (design note 0008): who is calling. `hypha-auth` holds identities with typed credentials (password, TOTP, recovery codes; stored as kind + lookup + JSON so a new login method needs no column), server-side sessions (a pending state while a second factor is owed), API keys, password resets and prefixed tokens stored only as SHA-256; hashing and sealing are ports (`PasswordHasher`, `SecretBox`), and its commands take one `env: &impl AuthEnv` bundling the non-storage ports. `hypha-users` holds roles (named scope sets; the owner role has every scope), users and invites, and the staff flows (`login`, `accept_invite`, `authenticate_staff`). Nobody grants a scope they lack (`require_grantable`); a write scope implies its read scope (`Scope::implied_by`, applied in `Ctx::has_scope`).
- `hypha-testkit`: in-memory repos for every port (`InMemoryProductRepo`, `InMemoryCartRepo`, …) and deterministic ports (`SequentialIds`, `FixedClock`), for the domain crates' fast command tests (hosts run on Postgres only and don't depend on it). It depends on domain crates, so domain crates use it only as a dev-dependency from their `tests/` folder.
- `hypha-http` and `hypha-host-axum` (design note 0026, W3): `hypha-http` is the HTTP layer as a library that builds for wasm (routes, extractors, errors, DTOs, OpenAPI, `AppState`, the job steps in `jobs.rs`); what only a runtime can do comes from the host through `host.rs`'s capabilities (`HostClock`, `HostIds`, `HostRandom`, `Offload` for CPU-heavy work, `HostBackground`, `HostLimiter`, `HostCalls` for merchant URLs, `HostHttp` for the media storage, `HostMail` for email (`email::LogSender` is the portable `log` sender; SMTP is the native host's `email.rs`, Resend `hypha-mail-resend`), `AfterWrites`), each a shared function with boxed `Send` futures, and the client's address from the host-set `client_ip::PeerAddr`. `hypha-host-axum` is the native host: `main.rs` (startup, config, serving), `storage.rs` (`PgDatabase`: the deadpool pool with statement caches, migrated; `PgStorage`: it and the handlers built at startup), `runner.rs` (the job runner and its wake-ups), `limiter.rs` (`governor`), `calls.rs` (`reqwest` with the public-address resolver), `platform.rs` (system clock, UUIDv7, OS randomness, blocking threads, background slots), and the route tests (`route_tests.rs`; they send with a recording `HostMail`, `TestApp::emails`, never the configured sender, so they need no SMTP server). Together they're the only place with Tokio, HTTP, auth parsing, logging subscribers (`tracing`) and real ID generation (`UuidV7Ids`, in the native host). `routes/` holds one module per area with its own request/response DTOs (never serialize domain types directly); `error.rs` maps every crate's `CommandError` to a status (403 scope, 404 resource in the URL, 409 conflict or the state of the resource in the URL, 422 invalid input incl. unknown IDs in the body (except the routes listed at the top of `error.rs` that store other domains' IDs unchecked), 500 storage with the message hidden) and fills `details` for errors that carry data a client acts on (shortages, unavailable lines, totals); `extract.rs` wraps `Json`/`Path` so even axum's rejections return `{"code": …, "error": …, "details": …}`; routes whose command takes an idempotency key use `KeyedJson` (reads the `Idempotency-Key` header, fingerprints the request) and `idempotent_response`. Request DTOs are `#[serde(deny_unknown_fields)]`; PATCH bodies follow JSON Merge Patch (absent keeps, `null` clears) via the `patch::nullable` / `patch::non_null` field helpers. List routes (design note 0012) share `routes/page.rs`: they take `ListQuery<Filters>` (the page's `cursor`/`limit` read apart from the route's own `deny_unknown_fields` filters), list `PageParams` and the filters in `params(...)` (the documents add the paging errors to routes with exactly those parameters), and return a `PageResponse<ItemDto>` named by a type alias (`type ProductPage = PageResponse<ProductResponse>;`). Storage is `PgStorage` (`hypha-host-axum`'s `storage.rs`; deadpool pool, one `PgStore` per request) behind the `Storage` trait, the seam a Workers storage would plug into; handlers are generic over it and get the request's ports from `caller.authenticate(&state)` (see below). Routes are listed once, in the `route_table!` macro in `routes/mod.rs` (`[surface, METHOD, "/path", module::handler]`): it builds the router per concrete storage (axum can only prove handler futures `Send` for concrete types) and the OpenAPI documents (`routes/openapi.rs`). There are two API surfaces (design note 0010): `/admin/*` (staff sessions and secret keys) and `/storefront/*` (publishable keys), each with its own DTOs where they differ (a storefront never sees drafts or admin fields). A new route is a table row plus a handler with `#[utoipa::path(...)]` (method and path as in the table, `params`, `request_body`, the success response, and `extensions(("x-hypha-scopes" = json!([...])))`) and `utoipa::ToSchema` on its DTOs; operation IDs, tags, security and the standard error responses are added from the table. Without the annotation the table doesn't compile. Every handler takes a `Caller` (`Caller<Admin>`, the default, or `Caller<Storefront>`; the wrong kind of credential for the surface is a 403 before any lookup) (`extract.rs`), the one place a request becomes a `Ctx`: the extractor only reads `Authorization: Bearer` (a staff session `hypha_sess_…`, the role's scopes read fresh each request, or an API key `hypha_sk_…` / `hypha_pk_…`) or `X-Publishable-Key` (none is 401 `unauthenticated`), and the handler's first line is `let (ports, ctx) = caller.authenticate(&state).await?;` (a bad token is 401 `invalid_token`): one pooled connection per request, and the only way to ports besides `state.public_ports()`, which is for routes that need no credentials. Parse bodies only after that: `JsonBody` and `KeyedJson` buffer the bytes, and `body.parse()?` / `req.parse()?` come after `authenticate`, so strangers get a 401 before any JSON work. `/me` routes take `StaffCaller` the same way (API keys get 401 `session_required`). The public routes (login, MFA, password reset, invite acceptance) take a `ClientIp` (`client_ip.rs`) and call `rate_limit::enforce(&state.limiter, Rule::…, key)` per address before parsing and per email after (`429 rate_limited` with `Retry-After`); every limit is a `Rule` with its quota in `rate_limit.rs`, behind the `RateLimiter` port (in memory natively (`limiter.rs`), the Rate Limiting binding on Workers). Work that must outlive the response runs in `state.background` (natively a few slots, drained on shutdown; `waitUntil` on Workers), spawned per concrete storage (`Storage::spawn_password_reset`) for the same `Send` reason as `router!`. Timed work (delivering events, pruning, the media sweep) is `hypha-http`'s steps in `jobs.rs`, run natively by `runner.rs` (started in `serve`, stopped on shutdown; an idle job backs off to `jobs.idle_interval`; `AfterWrites` wakes the dispatcher when a request's ports commit events or retry a delivery (`hypha_core::SignalsDispatch`, set in `AppState::public_ports`), and a dispatch step that did work wakes search sync); each job is a step from a domain crate (`hypha_dispatch::fan_out`, …) that says whether there's more, so a Workers host can call the same steps from a Cron trigger. `HostEnv` (`state.rs`) provides randomness and Argon2id through the host's `Runtime` (`Offload`: blocking threads natively), the `SecretBox` under `HYPHA_SECRET_KEY`, and orders' access tokens (`OrderTokens`, shared with `MailHost` for the emails' links); the staff flows' emails go through `StaffEnv` (`mail.rs`). The router for a concrete storage is `hypha_http::router!(PgStorage)` (handlers and their DTO types are `pub` so it can expand in the host's crate).

Command shape (see `crates/hypha-products/src/commands.rs`): `async fn cmd(ctx: &Ctx, repo: &impl Repo, ids: &impl IdGenerator, input: RawInput) -> Result<_, CommandError>`; first line `ctx.require(Scope::...)?`, then validate raw input through domain constructors. `CommandError` composes lower errors via `#[from]`.

When a command needs more than one repository, take `ports: &S` bound on the accessor traits it uses: each crate defines `HasXxx` (associated repo type + `fn xxx(&self)`) next to its repo traits in `repo.rs`, e.g. `create_cart<S: HasMarkets + HasCarts>`. A composing crate names its union with a blanket impl (`CartPorts`, `PricingPorts` in `crates/hypha-cart/src/commands.rs`), so implementors never list them. Hosts and tests implement the accessors once (`hypha_testkit::InMemoryPorts`, `PgStore`); a new repository adds one `HasXxx`. Static dispatch keeps `Send` provable; don't bundle them into `&dyn` objects.

## Hard constraints

- Core and domain crates must compile for `wasm32-unknown-unknown`: no Tokio, threads, `std::fs`, `SystemTime::now()` or random UUID generation there. Time, IDs and randomness come in through ports.
- Repository traits use `async fn` with `#[allow(async_fn_in_trait)]` and **no `Send` bound**, on purpose (Cloudflare futures are `!Send`). Hosts use concrete types/generics so the compiler can prove `Send`; never `&dyn` for ports used across `.await`.
- Authorization lives in commands (`ctx.require(Scope::...)?`); authentication lives in hosts. Commands never trust raw input.

## Code standards

- Money: integer minor units (`i64`), never floats, capped at ±`Money::MAX_AMOUNT` (2⁵³ − 1) so JSON clients represent every amount exactly; `Money::new` is fallible. Checked arithmetic returning `Result`; percentages as `BasisPoints` with round-half-away-from-zero; `i128` for intermediates.
- Newtypes with validated constructors for anything with rules (`Handle`, `Price`, `CountryCode`, IDs). Don't derive `Deserialize` on validated types unless via `#[serde(try_from = ...)]`.
- IDs: `define_id!` macro in `hypha-core/src/ids.rs` — UUID inside, prefixed string at the edges (`prod_…`, `var_…`, `mkt_…`, `pl_…`). Store native UUIDs; UUIDv7 in hosts.
- Errors: `thiserror` enums with specific variants (no stringly errors). Every error enum implements `hypha_core::ErrorCode` with an exhaustive `match` (no `_` arm): stable snake_case codes, never renamed once released, wrappers delegate to the inner error. Messages use `Display` for domain values (`EUR`, `active`); raw input the caller sent (a string or char that failed to parse) is quoted with `{0:?}`, so blanks and control characters stay visible. No `unwrap`/`expect`/panics in non-test code except documented invariants.
- Aggregates own their children (Product owns Variants); cross-aggregate rules live in commands/functions above them.
- Migrations are per module: `hypha_store_postgres::CORE` is core's `MigrationSet`; a spore ships its own set (module `"spore_<name>"`, tables prefixed the same way), passed to `migrate(&mut client, &[CORE, …])`. Append only: an applied migration is never edited, renamed or reordered (the runner checks names and fails).
- Postgres queries (design note 0025, §6): repositories take `&impl Queries` (`hypha-store-postgres`'s `store.rs`), never `&impl GenericClient`, and query with `tokio-postgres`'s typed names (`query_typed`, `query_typed_opt`, …) through it: `consistent_read!(conn, |tx| …)` / `in_transaction!` hand out a `Db` with the connection's `StatementCache` (prepared once per pooled connection; none on Workers or with `database.statement_cache = false`), and `conn.db()` outside a transaction. A load with child rows selects them through the root's filter (a join on the root table) and sends its queries together with `try_join*`, pipelined in one round trip, rather than waiting for the root's IDs (see `products.rs`'s `load`).
- Persistence (design note `docs/design/0001-postgres-storage.md`): aggregate roots implement `Versioned`; repos have `insert(&mut T)` / `update(&mut T)`, never an upsert. `update` from an old version fails with `RepoError::StaleVersion`. Uniqueness rules are repo `keys::*` constants reported as `RepoError::Duplicate(key)`; commands keep a read-then-check for precise errors **and** map the `Duplicate` from the write to the same domain error (a race must look like a normal duplicate). In-memory repos are built on `hypha-testkit`'s `Table`, which enforces versions and keys like a database. A command writes one aggregate through its repo, or several through one `HasBatch` commit (`hypha-core/src/ports.rs`): each crate has a `StageXxx` trait next to its repo trait (`StageCarts`), implemented by the adapters' batch types (`InMemoryBatch`, `PgBatch`), and staging moves the aggregate to the version it gets on commit. `reserve_stock` / `release_stock` (no batch of their own) still write every item at once through `InventoryItemRepo::update_many`, all or nothing (0004, I7). Domain events (design note 0016): an aggregate records them (`hypha_core::Recorded`; a `Recorder`, or a coalescing type like products' `Changes`), and every write of it (repo `insert`/`update`, `Stage*` in a batch) takes them and writes them to `outbox_events` in the same transaction, stamped with the ports' actor (`ActingAs`, set in `Caller::authenticate`); set-based writes (catalog membership, fixed prices, tax-class assignment) are staged in a batch with their events (`StageCatalogProducts`, `StageEvents`, …); the repos' own set-based methods record nothing and are for setting up data. Take an aggregate's events before copying it into a batch, so the stored copy carries none. Aggregate roots also carry `Stamps` (`created_at`/`updated_at`, `hypha_core::Stamped`): adapters set them with `stamp_insert`/`stamp_update` from the ports' clock (`PgStore::new(conn, clock)`; in memory, the shared `InMemoryOutbox`'s fixed clock) before taking the snapshot, in repo writes and when staging. Payloads are contract types in the domain crate's `events.rs` (subject and what changed, not the aggregate; a reshaped field is a new version). `restore` re-runs constructor rules, so tightening a rule (a shorter max length, a newly required field) needs a migration that fixes or rejects existing rows first, or those rows stop loading (500).
- Getters return values for `Copy` types and references (`&str`, slices) for owned heap data.
- Workspace lints: `unsafe_code = "forbid"`, `clippy::all = "warn"`. Code must be fmt-clean and clippy-warning-free.

## Testing

- Unit tests in `#[cfg(test)] mod tests` at the bottom of each file; one rule per test; test boundaries (0 vs -1, exact rounding halves); compare expected errors exactly with `assert_eq!(result, Err(...))`, never via `unwrap`.
- Command tests are integration tests in each crate's `tests/` folder using `hypha-testkit` (avoids duplicate-crate issues with dev-dependencies).
- Async in tests via `pollster::block_on`; deterministic IDs via `SequentialIds` and `Uuid::from_u128(n)`; time via `FixedClock` (commands take `clock: &impl Clock` like `ids`).
- Repository contract: `hypha_testkit::contract::{product_repo, product_list, market_repo, catalog_repo, price_list_repo, cart_repo, tax_class_repo, tax_region_repo, location_repo, inventory_item_repo, customer_repo, order_repo, fulfillment_repo, payment_method_repo, payment_method_delete, payment_repo, payment_batch, idempotency_repo, batch, identity_repo, session_repo, api_key_repo, password_reset_repo, user_repo, role_repo, invite_repo, staff_sessions, staff_batch, asset_repo, asset_usages, shipping_zone_repo, app_provider_repo, app_repo, oauth_repos, outbox, search_index, search_queue, search_settings_repo, channel_repo, category_repo, notification_template_repo, notification_settings_repo, notification_repo, notification_settings_batch}` and `blob_store` (file storage: run with the client's upload and download as closures; the S3 adapter runs it against MinIO) define what every repo adapter must do (round trips, versions, unique keys, batched methods). The suite is behind testkit's `contract` feature (so hosts don't ship it): adapters enable it as a dev-dependency, and the in-memory run (`crates/hypha-testkit/tests/contract.rs`) needs `--features contract` when testing that crate alone (`cargo test --workspace` enables it). Every new adapter must run it. Batch methods state caller preconditions (parent exists, no duplicates) in their docs, and the contract checks that breaking them fails. When a repo trait gains a method or a unique key, add a contract scenario first.
